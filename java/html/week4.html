i Overview & TL;DR

TL;DR
  • volatile = visibility, KHÔNG atomic; count++ vẫn race.
  • Double-checked locking cần volatile vì cấm reorder "gán reference trước constructor xong".
  • CAS lock-free; ABA khắc phục bằng AtomicStampedReference.
  • AQS = state + hàng đợi FIFO; nền của ReentrantLock/Semaphore.
  • ThreadPool: core→queue→max→reject; tránh newFixedThreadPool (queue vô hạn → OOM).
  • Virtual thread (Loom) hợp IO-bound; pinning trong synchronized.

1 Java Memory Model

Vấn đề reordering + cache

Mỗi core có cache riêng; compiler + CPU có thể reorder lệnh để tối ưu. Thread A ghi 2 biến theo thứ tự này, thread B có thể thấy theo thứ tự khác.

int x = 0; boolean ready = false;
// Thread A:            // Thread B:
x = 42;                 while (!ready) {}
ready = true;           print(x);  // có thể in 0!

Không có happens-before giữa ghi của A và đọc của B → B có thể thấy ready=true nhưng x=0. Fix: volatile boolean ready.

happens-before — quy tắc chính
  • Program order: trong 1 thread, lệnh trước hb lệnh sau.
  • Monitor: unlock hb mọi lock sau đó trên monitor đó.
  • volatile: ghi volatile hb mọi đọc sau đó.
  • Thread start/join: start hb hành động trong thread; hành động trong thread hb join.
  • Transitivity: A hb B, B hb C ⇒ A hb C.

2 volatile

  • Đảm bảo visibility (đọc thấy ghi mới nhất) + cấm reorder (memory barrier).
  • KHÔNG đảm bảo atomicity: count++ (read-modify-write) vẫn race.
Double-checked locking cần volatile
private static volatile Singleton instance;   // volatile BẮT BUỘC
if (instance == null)
    synchronized (lock) {
        if (instance == null) instance = new Singleton();
    }

new Singleton() = cấp bộ nhớ → chạy constructor → gán reference. CPU có thể reorder gán reference trước khi constructor xong → thread khác thấy instance != null nhưng chưa init. volatile cấm reorder này.

3 CAS, Atomic & ABA

CAS (Compare-And-Swap)
AtomicInteger c = new AtomicInteger(0);
c.incrementAndGet();   // đọc v -> tính v+1 -> CAS(v, v+1); fail thì retry (spin)

Thao tác phần cứng nguyên tử: nếu giá trị hiện tại == kỳ vọng thì ghi giá trị mới. Lock-free, nhanh khi tranh chấp thấp. Tranh chấp cao → nhiều retry → cân nhắc LongAdder (chia cell).

Bài toán ABA

CAS chỉ so giá trị, không biết A→B→A. Thread thấy vẫn "A" nên CAS thành công dù trạng thái đã đổi (vấn đề với cấu trúc lock-free dùng con trỏ). Khắc phục: AtomicStampedReference (gắn version/stamp).

4 synchronized

synchronized block → bytecode monitorenter/monitorexit; method → flag ACC_SYNCHRONIZED. Mỗi object có monitor (gắn mark word), reentrant.

5 AQS

AbstractQueuedSynchronizer

Khung nền cho ReentrantLock, Semaphore, CountDownLatch, ReadWriteLock. Giữ volatile int state (ý nghĩa tùy lock) + hàng đợi FIFO thread chờ (CLH). Thread không giành được → LockSupport.park() (không spin lãng phí), được nhả thì unpark.

Primitive dựa AQS: Semaphore(n) (n permit), CountDownLatch(n) (chờ n sự kiện, 1 lần), CyclicBarrier(n) (chờ nhau, tái dùng), ReadWriteLock (nhiều reader).

Bẫy Executors factory

newFixedThreadPool/newSingleThreadExecutor dùng LinkedBlockingQueue không giới hạn → task dồn vô hạn → OOM thay vì reject (bước 3-4 không xảy ra). newCachedThreadPool tạo thread không giới hạn. Nên tự tạo ThreadPoolExecutor với bounded queue + rejection policy.

Rejection: AbortPolicy (ném exception), CallerRunsPolicy (chạy trên thread gọi → back-pressure), Discard/DiscardOldest.

7 CompletableFuture

CompletableFuture
    .supplyAsync(() -> fetchUser(id), executor)  // nên truyền executor riêng
    .thenApply(User::name)                        // map
    .thenCompose(n -> fetchOrdersAsync(n))         // flatMap nối future
    .thenCombine(other, (a, b) -> merge(a, b))     // gộp 2 future song song
    .exceptionally(ex -> fallback())              // xử lý lỗi
    .orTimeout(2, TimeUnit.SECONDS);
  • thenApply chạy trên thread hoàn thành stage trước; thenApplyAsync chạy trên pool khác.
  • Mặc định dùng ForkJoinPool.commonPool → production nên truyền executor riêng.
  • Exception lan dọc chain, thenApply bị skip tới khi gặp exceptionally/handle.

8 False sharing

Bug hiệu năng tinh vi

CPU cache theo cache line (~64 byte). Hai biến khác nhau cùng cache line → thread A ghi biến X invalidate cache line ở core đang đọc biến Y (dù Y không đổi) → giảm hiệu năng nghiêm trọng trong hot loop đa luồng. Giải: padding hoặc @Contended. LongAdder thắng AtomicLong khi contention cao một phần nhờ tách cell tránh false sharing.

9 Virtual threads (Loom, Java 21)

Platform thread

Map 1-1 OS thread (~1MB stack, giới hạn vài nghìn, tạo/switch tốn kém).

Virtual thread

Nhẹ, JVM lập lịch trên tập nhỏ carrier thread. Block IO → unmount khỏi carrier → carrier chạy vt khác. Tạo được hàng triệu.

Dùng khi

Workload IO-bound nhiều kết nối — viết code blocking đơn giản thay vì async callback. KHÔNG tăng tốc CPU-bound.

Pinning

Virtual thread block trong synchronized hoặc native call → bị ghim vào carrier (không unmount) → giảm lợi ích. Khuyến nghị dùng ReentrantLock thay synchronized trong đoạn có blocking.

10 Deadlock & chẩn đoán

4 điều kiện Coffman

mutual exclusion + hold-and-wait + no preemption + circular wait. Phá 1 điều kiện là hết deadlock.

Cách tránh + chẩn đoán
  • Lock ordering: giữ khoá theo cùng thứ tự (vd id tăng dần) → phá circular wait.
  • tryLock(timeout) → nhả và thử lại thay vì chờ vô hạn.
  • jstack <pid> → "Found one Java-level deadlock" + chu trình khoá.
ThreadLocal + pool = leak

Thread pool tái dùng thread → phải threadLocal.remove() (trong finally) sau khi xong, nếu không dữ liệu rò rỉ sang task sau và giữ object không cho GC.

11 Follow-up questions

Interviewer hay đào tiếp
  • Vì sao double-checked locking cần volatile? → cấm reorder gán reference trước constructor xong.
  • volatile có làm count++ an toàn? → không.
  • CAS/ABA khắc phục thế nào? → AtomicStampedReference.
  • ThreadPool xử lý task thứ tự nào? → core → queue → max → reject.
  • Vì sao tránh newFixedThreadPool? → queue vô hạn → OOM.
  • AQS là gì? → state + hàng đợi FIFO; park/unpark.
  • False sharing? → 2 biến cùng cache line; padding/@Contended.
  • Virtual thread pinning? → block trong synchronized/native ghim vào carrier.
  • happens-before của volatile/lock? → ghi volatile hb đọc; unlock hb lock.
  • LongAdder thắng AtomicLong khi nào? → contention cao (tách cell).

? Flashcards

QJMM giải quyết vấn đề gì?+

Định nghĩa khi nào một thread thấy được ghi của thread khác, và cho phép compiler/CPU reorder lệnh miễn không đổi ngữ nghĩa đơn luồng. Không đồng bộ → thread có thể thấy ghi theo thứ tự khác hoặc giá trị cũ.

Qhappens-before, kể các quy tắc chính?+

Program order (trong 1 thread), monitor (unlock hb lock cùng monitor), volatile (ghi hb đọc), thread start (start hb hành động trong thread), thread join, và transitivity. Nếu A hb B thì mọi ghi trước A thấy được ở B.

QVì sao while(!ready){} print(x) có thể in giá trị cũ của x?+

Không có happens-before giữa ghi của thread A và đọc của B. B có thể thấy ready=true nhưng x chưa được flush/reorder → in 0. Fix: khai báo ready volatile để tạo happens-before.

Qvolatile đảm bảo gì, không đảm bảo gì?+

Đảm bảo visibility (đọc thấy ghi mới nhất) + cấm reorder (memory barrier). KHÔNG đảm bảo atomicity: count++ vẫn race. Dùng cho flag, publish reference, double-checked locking.

QVì sao double-checked locking cần volatile?+

instance = new Singleton() gồm cấp bộ nhớ, chạy constructor, gán reference. CPU có thể reorder gán reference TRƯỚC khi constructor xong → thread khác thấy instance != null nhưng chưa init. volatile cấm reorder.

QCAS hoạt động thế nào?+

Compare-And-Swap: thao tác phần cứng nguyên tử, nếu giá trị hiện tại == kỳ vọng thì ghi giá trị mới. incrementAndGet lặp: đọc v, tính v+1, CAS(v,v+1), fail thì retry. Lock-free, nhanh khi tranh chấp thấp.

QBài toán ABA là gì? Khắc phục?+

CAS chỉ so giá trị, không biết A→B→A đã xảy ra. Thread thấy vẫn "A" nên CAS thành công dù trạng thái đã đổi. Vấn đề với cấu trúc lock-free (con trỏ node). Khắc phục: AtomicStampedReference (gắn version/stamp).

QKhi nào LongAdder tốt hơn AtomicLong?+

Contention cao. AtomicLong nhiều thread cùng CAS một biến → nhiều retry (spin lãng phí) + false sharing. LongAdder chia thành nhiều cell, mỗi thread cộng vào cell riêng, tổng khi cần → giảm tranh chấp.

QLock upgrade của synchronized?+

biased → lightweight (CAS spin trên mark word) → heavyweight (OS mutex, park thread). Biased locking đã bỏ mặc định từ Java 15. Heavyweight tốn context switch vào kernel.

QAQS là gì?+

AbstractQueuedSynchronizer: khung nền cho ReentrantLock/Semaphore/CountDownLatch. Giữ volatile int state (ý nghĩa tùy lock) + hàng đợi FIFO thread chờ. Thread không giành được thì LockSupport.park (không spin lãng phí).

Qsynchronized vs ReentrantLock?+

synchronized tự nhả khoá, đơn giản. ReentrantLock (AQS): tryLock/timeout, lockInterruptibly, fairness, nhiều Condition, nhưng phải unlock trong finally. Cả hai reentrant.

QCountDownLatch vs CyclicBarrier?+

CountDownLatch: chờ n sự kiện (countDown → await), dùng 1 lần. CyclicBarrier: n thread chờ nhau tại điểm hẹn, tái sử dụng được (reset sau mỗi vòng).

QThreadPoolExecutor xử lý task theo thứ tự nào?+

1) < corePoolSize → tạo thread mới. 2) đủ core → vào queue. 3) queue đầy & < max → tạo thread tới max. 4) queue đầy & đạt max → rejection handler.

QVì sao tránh Executors.newFixedThreadPool trong production?+

Dùng LinkedBlockingQueue KHÔNG giới hạn → task dồn vô hạn → OOM thay vì back-pressure (bước tạo thread tới max/reject không xảy ra). Nên tự tạo ThreadPoolExecutor với bounded queue + rejection policy.

QCallerRunsPolicy làm gì?+

Khi pool quá tải, task bị từ chối sẽ chạy trên thread gọi submit → làm chậm producer → tạo back-pressure tự nhiên, tránh dồn task vô hạn.

QthenApply vs thenApplyAsync?+

thenApply chạy trên thread hoàn thành stage trước (có thể chiếm thread đó). thenApplyAsync chạy trên pool khác. Production nên truyền executor riêng thay vì mặc định ForkJoinPool.commonPool.

QCompletableFuture xử lý exception thế nào?+

Exception lan dọc chain, stage thenApply bị skip cho tới khi gặp exceptionally(fn) (fallback) hoặc handle((r,e)->...) (cả 2 nhánh). thenCompose = flatMap nối future, thenCombine gộp 2 future song song.

QFalse sharing là gì?+

CPU cache theo cache line (~64 byte). 2 biến khác nhau cùng cache line: ghi biến X invalidate cache line ở core đang đọc biến Y (dù Y không đổi) → chậm trong hot loop đa luồng. Fix: padding hoặc @Contended.

QVirtual thread vs platform thread?+

Platform map 1-1 OS thread (~1MB, vài nghìn). Virtual (Loom) nhẹ, JVM lập lịch trên carrier thread, unmount khi block IO → triệu cái, hợp IO-bound. Không tăng tốc CPU-bound.

QVirtual thread pinning là gì?+

Nếu virtual thread block trong synchronized hoặc native call, nó bị ghim vào carrier thread (không unmount) → giảm lợi ích. Khuyến nghị dùng ReentrantLock thay synchronized trong đoạn có blocking.

Q4 điều kiện deadlock và cách tránh?+

mutual exclusion, hold-and-wait, no preemption, circular wait. Tránh: lock ordering (thứ tự cố định phá circular wait), tryLock timeout, giảm phạm vi/số khoá. Chẩn đoán: jstack phát hiện deadlock.

QThreadLocal bẫy gì trong thread pool?+

Thread tái dùng nên phải remove() sau khi xong (trong finally), nếu không dữ liệu rò rỉ sang task sau và giữ object không cho GC → memory leak.
