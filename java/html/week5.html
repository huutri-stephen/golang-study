i Overview & TL;DR

TL;DR
  • Class loading: Loading → Linking (verify/prepare/resolve) → Initialization; lazy.
  • Parent delegation: App→Platform→Bootstrap; 2 loader = 2 class.
  • TLAB: cấp phát không đồng bộ trong Eden; escape analysis → scalar replacement.
  • Card table: theo dõi reference old→young để minor GC không quét cả old.
  • G1 (mặc định) region-based; ZGC pause <1ms (colored pointer + load barrier).
  • Leak dù có GC = reachable nhưng không cần (static/ThreadLocal/classloader).

Metaspace vs PermGen

Metaspace (J8+) ở native memory, tự grow (giới hạn MaxMetaspaceSize). PermGen cũ ở trong heap, cố định, hay gây OOM: PermGen. String pool chuyển từ PermGen sang heap ở J7.

5 Object allocation: TLAB

Thread-Local Allocation Buffer

Heap cấp phát bằng bump-the-pointer (tăng con trỏ trong Eden) — rất nhanh. Nhiều thread cùng cấp phát sẽ tranh con trỏ → mỗi thread có TLAB (vùng riêng trong Eden) cấp phát không cần đồng bộ. Hết TLAB thì xin block mới (hiếm).

Escape analysis + scalar replacement

JIT phân tích nếu object không thoát khỏi method → có thể không cấp trên heap mà tách thành biến trên stack (scalar replacement) → giảm áp lực GC, đôi khi bỏ luôn lock (lock elision).

6 GC nền tảng

Reachability, không reference counting

Từ GC roots (biến local stack, static field, JNI ref, active thread, monitor) đi theo reference đánh dấu object reachable; không reachable là rác. Không reference counting vì không xử lý được tham chiếu vòng (A↔B).

Object mới → Eden. Minor GC copy sống sót sang survivor, tăng age; qua ngưỡng → promote lên old. Major/Full GC dọn old (đắt hơn).
Card table (vì sao minor GC không quét cả old)

Object old trỏ tới object young → minor GC làm sao biết young đó còn sống? Chia old thành card (512B); write barrier đánh dấu card "dirty" khi ghi reference old→young. Minor GC chỉ quét card dirty. G1 dùng remembered set per-region tương tự.

7 G1 chi tiết

Region-based

Heap chia ~2048 region đều (1-32MB), vai trò linh hoạt (Eden/Survivor/Old/Humongous ≥ 1/2 region). "Garbage First": ưu tiên thu region nhiều rác nhất để tối đa bộ nhớ thu / pause target.

3 loại thu gom

Concurrent mark

Mixed GC
STW, young + old rác nhất
-XX:MaxGCPauseMillis=200 (mặc định): G1 chọn số region thu vừa đủ để đạt target. Cân bằng throughput/latency.

8 ZGC & low-latency

Pause <1ms

Mục tiêu pause dưới 1ms, gần như không phụ thuộc heap size (kể cả nhiều TB). Kỹ thuật: colored pointers (nhét metadata GC vào bit con trỏ 64-bit) + load barrier (khi đọc reference, kiểm/relocate object đang di chuyển) → hầu hết GC chạy concurrent, chỉ vài pha STW cực ngắn.

Leak dù có GC (reachable nhưng không cần)
  • Static collection giữ mãi (cache không evict).
  • Listener/callback không hủy đăng ký.
  • ThreadLocal không remove() trong thread pool (ThreadLocalMap value là STRONG ref, thread sống mãi → giữ value).
  • Key HashMap sai equals/hashCode hoặc mutable key.
  • ClassLoader leak: giữ reference tới class của classloader (redeploy) → cả classloader + class không unload → Metaspace phình.

? Flashcards

Q5 bước class loading?+

Loading (đọc .class, tạo Class object) → Linking gồm Verification (kiểm bytecode an toàn), Preparation (cấp static field giá trị mặc định), Resolution (symbolic→direct reference) → Initialization (chạy <clinit>). Lazy: init khi lần đầu chủ động dùng.

QTruy cập static final int B = 10 có kích hoạt class init không?+

Không. Hằng compile-time được inline vào call site lúc compile, không kích hoạt <clinit>. Truy cập static field non-final hoặc gọi static method thì có.

Q<clinit> có thread-safe không? Ứng dụng?+

Có, JVM đảm bảo <clinit> chạy đúng 1 lần, lock trên Class. Nền của initialization-on-demand holder idiom: lazy singleton qua static nested Holder class, không cần volatile/synchronized.

QParent delegation model làm gì?+

ClassLoader hỏi cha trước khi tự load: App→Platform→Bootstrap. Đảm bảo class core (java.lang.String) luôn do bootstrap load (chống giả mạo), tránh trùng class. Hai class cùng tên khác loader = hai class khác nhau.

QMetaspace khác PermGen thế nào?+

Metaspace (Java 8+) ở native memory, tự grow (giới hạn MaxMetaspaceSize). PermGen (cũ) ở trong heap, kích thước cố định, hay gây OOM: PermGen. String pool cũng chuyển từ PermGen sang heap ở Java 7.

QStackOverflowError vs OutOfMemoryError?+

SOF: JVM stack của một thread đầy (đệ quy quá sâu). OOM: heap/metaspace/native đầy. Stack là per-thread (frame biến local); heap chia sẻ (object).

QTLAB là gì, giải quyết vấn đề gì?+

Thread-Local Allocation Buffer: mỗi thread có vùng riêng trong Eden để cấp phát object bằng bump-pointer KHÔNG cần đồng bộ. Tránh nhiều thread tranh con trỏ cấp phát chung. Hết TLAB mới xin block mới.

QEscape analysis + scalar replacement?+

JIT phân tích nếu object không thoát khỏi method thì có thể không cấp trên heap mà tách thành các biến trên stack (scalar replacement) → giảm áp lực GC, đôi khi bỏ luôn lock (lock elision).

QGC xác định rác thế nào? Vì sao không reference counting?+

Reachability: từ GC roots (biến local stack, static field, JNI, active thread) đánh dấu object reachable; không reachable là rác. Không dùng reference counting vì không xử lý được tham chiếu vòng (A↔B).

QWeak generational hypothesis?+

Hầu hết object chết trẻ. Nên chia young (Eden+Survivor) và old. Minor GC dọn young thường xuyên và rẻ (ít object sống); object sống sót được promote lên old. Major/full GC dọn old, đắt hơn.

QCard table dùng để làm gì?+

Giải quyết reference old→young. Chia old thành card 512 byte; write barrier đánh dấu card "dirty" khi ghi reference. Minor GC chỉ quét card dirty thay vì cả old gen → nhanh. G1 dùng remembered set per-region tương tự.

QVì sao G1 tên "Garbage First"?+

Heap chia ~2048 region kích thước đều, vai trò linh hoạt (Eden/Survivor/Old/Humongous). G1 ưu tiên thu region NHIỀU RÁC NHẤT trước để tối đa bộ nhớ thu về trong pause target (MaxGCPauseMillis).

QG1 có mấy loại thu gom?+

Young GC (STW, thu Eden+Survivor), Concurrent marking (đánh dấu old song song app, SATB), Mixed GC (STW, thu young + một số old region rác nhất). Cân bằng throughput/latency.

QZGC đạt pause <1ms bằng cách nào?+

Colored pointers (nhét metadata GC vào bit con trỏ 64-bit) + load barrier (kiểm/relocate object khi đọc reference). Hầu hết công việc GC chạy concurrent với app, chỉ vài pha STW cực ngắn, gần như không phụ thuộc heap size.

QStrong/soft/weak/phantom reference?+

Strong: không thu khi còn. Soft: thu khi sắp thiếu bộ nhớ (cache). Weak: thu ở GC kế nếu chỉ còn weak (WeakHashMap). Phantom: enqueue vào ReferenceQueue sau finalize để cleanup off-heap (thay finalize).

QThreadLocal leak trong thread pool vì sao?+

ThreadLocalMap dùng weak key nhưng value là STRONG ref. Thread pool sống mãi → nếu không remove(), value bị giữ qua thread → leak. Luôn remove() trong finally sau khi dùng.

QClassLoader leak là gì?+

Giữ reference tới class/instance của một classloader (thường khi redeploy app) → cả classloader và mọi class nó nạp không được unload → Metaspace phình dần tới OOM Metaspace.

QCác loại OutOfMemoryError?+

Java heap space (leak/object nhiều), GC overhead limit exceeded (GC chạy mãi thu ít), Metaspace (quá nhiều class), unable to create native thread (quá nhiều thread), Direct buffer memory (NIO off-heap).

QQuy trình debug heap tăng dần dẫn tới OOM?+

Chụp heap dump (jmap -dump:live hoặc HeapDumpOnOutOfMemoryError) → mở Eclipse MAT → xem Leak Suspects + dominator tree tìm object giữ nhiều RAM và đường reference giữ nó (GC root path).

QApp CPU cao/treo, debug thế nào?+

jstack <pid> nhiều lần tìm thread RUNNABLE chiếm CPU hoặc BLOCKED (deadlock). top -H tìm thread OS nóng rồi map nid (hex) sang thread trong jstack. async-profiler cho flame graph CPU.

QFlag nào nên đặt cho production?+

-Xms=-Xmx (tránh resize), chọn GC (-XX:+UseG1GC), -Xlog:gc* để có GC log, -XX:+HeapDumpOnOutOfMemoryError + HeapDumpPath để tự chụp dump khi OOM phục vụ điều tra.
