i Overview & TL;DR

TL;DR
  • == → bytecode if_acmp* (so địa chỉ); .equals() → invokevirtual (nội dung).
  • new Object() = 16B; Integer = 16B vs int 4B → autoboxing tốn ~4x.
  • Integer cache -128..127; luôn .equals() cho wrapper.
  • String immutable (final class + final value); pool trong heap; concat J9+ dùng invokedynamic.
  • equals/hashCode contract: bằng nhau ⇒ cùng hashCode; quên hashCode = bug HashMap.
  • Exception đắt ở fillInStackTrace; không dùng cho control flow.

new Object() = 12B header + 4 pad = 16B. Integer = 12 + 4 (int) = 16B vs int chỉ 4B.
Mark word & klass pointer

Mark word giữ identity hashCode (lazy — tính lần đầu khi cần), thông tin lock (biased/lightweight/heavyweight), GC age. Klass pointer trỏ metadata class trong Metaspace. Mọi object alignment 8 byte.

int[] vs Integer[] trong hot path

int[] lưu 4B/phần tử liền mạch (cache-friendly). Integer[] lưu reference trỏ tới các Integer 16B rải rác → tốn RAM, nhiều cache miss, áp lực GC. Hot path dùng primitive array.

  • == → if_acmpeq/if_acmpne (reference); primitive → if_icmpeq (int) / lcmp (long).
  • .equals() → invokevirtual (dynamic dispatch, chạy code override).
Vì sao nhầm lẫn nguy hiểm

== trên wrapper/String đôi khi đúng do trùng cache/pool → tạo ảo giác code chạy được rồi vỡ ở dữ liệu khác. Bug âm thầm.

3 Autoboxing & Integer cache

Integer x = 100;   // compiler chèn Integer.valueOf(100)
int y = x;        // compiler chèn x.intValue()
IntegerCache (diễn giải)
public static Integer valueOf(int i) {
    if (i >= -128 && i <= IntegerCache.high)   // mặc định 127
        return IntegerCache.cache[i + 128];   // object CHUNG
    return new Integer(i);                     // ngoài cache -> mới
}
Integer a = 127, b = 127;   a == b;  // true  (cache)
Integer c = 128, d = 128;   c == d;  // false (2 object)

Cache -128..127 (chỉnh qua -XX:AutoBoxCacheMax). Long/Short/Byte/Character cũng cache -128..127; Boolean cache cả 2 giá trị.

NPE khi unbox null
int v = map.get("missing");   // get trả null -> null.intValue() -> NPE

4 String: pool, immutability, nối chuỗi

Immutability thực thi thế nào

Field value (byte[] từ J9, trước char[]) là private final, không setter, không leak reference. Class String là final → không kế thừa phá được. J9+ Compact Strings: byte[] + coder (LATIN1 1B/char cho ASCII) tiết kiệm ~50% RAM.

String s1 = "hi";              // ldc -> intern tự động, lấy từ pool
String s2 = "hi";              // cùng object trong pool
String s3 = new String("hi");  // object mới trên heap
s1 == s2;          // true
s1 == s3;          // false
s1 == s3.intern(); // true

String pool là bảng hash trong heap (từ J7; trước ở PermGen). Literal intern tự động lúc class load qua ldc trỏ CONSTANT_String.

Nối chuỗi: + biên dịch thành gì
  • J8: a + b → new StringBuilder().append(a).append(b).toString().
  • J9+: invokedynamic + StringConcatFactory → JIT sinh chiến lược tối ưu runtime.
  • Trong vòng lặp mỗi += tạo StringBuilder + String mới → O(n²). Dùng một StringBuilder ngoài loop → O(n).

Composition over inheritance

Kế thừa tạo coupling chặt (fragile base class), lộ toàn bộ API cha, Java chỉ đơn kế thừa. Ưu tiên composition (has-a) + interface trừ khi thực sự "is-a" và ổn định.

7 equals() & hashCode() – contract sâu

5 quy tắc equals + contract hashCode
  • Reflexive, Symmetric, Transitive, Consistent, và x.equals(null) = false.
  • a.equals(b) ⇒ bắt buộc a.hashCode()==b.hashCode(). Ngược lại không bắt buộc (collision hợp lệ).
Vi phạm + bẫy đối xứng khi kế thừa

Quên hashCode → 2 object equals rơi bucket khác → get/contains sai. Nếu lớp con thêm field vào equals → parent.equals(child) true nhưng child.equals(parent) false → vỡ symmetric. Giải: composition, hoặc record (final).

@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User u)) return false;   // null-safe + type + bind
    return id == u.id && Objects.equals(email, u.email);
}
@Override public int hashCode() {
    return Objects.hash(id, email);   // ĐÚNG field như equals
}
Vì sao số 31

Lẻ + nguyên tố → phân phối hash tốt. 31 * i == (i << 5) - i nên JIT tối ưu bằng shift-subtract. Object.hashCode mặc định là identity hashCode lưu lazy trong mark word (không phải địa chỉ vì GC di chuyển object).

9 Follow-up questions

Interviewer hay đào tiếp
  • new Object() bao nhiêu byte? → 16 (12 header + 4 pad).
  • Identity hashCode lưu ở đâu? → mark word, không phải địa chỉ.
  • a+b+c String J8 vs J9? → J8 StringBuilder; J9 invokedynamic một lần.
  • Vì sao Integer cache -128..127? → tối ưu giá trị nhỏ hay dùng.
  • Gọi overridden method trong ctor cha thấy gì? → giá trị mặc định field con.
  • Vì sao record không phá đối xứng equals? → final, equals so tất cả component.
  • == bytecode reference vs int? → if_acmp* vs if_icmp*.
  • Compact Strings tiết kiệm gì? → byte[] LATIN1 cho ASCII, ~50% RAM.

? Flashcards

QMột object rỗng new Object() chiếm bao nhiêu byte?+

16 byte trên HotSpot 64-bit: 8B mark word + 4B klass pointer (compressed oops) = 12B header, pad lên bội số 8 → 16B. Mọi object alignment 8 byte.

QInteger chiếm bao nhiêu byte so với int?+

int = 4B (primitive). Integer = 12B header + 4B value = 16B object trên heap + reference 4/8B trỏ tới. Autoboxing tốn ~4x bộ nhớ + áp lực GC → tránh trong hot path.

QMark word lưu gì?+

Identity hashCode (lazy, tính lần đầu khi cần), thông tin lock (biased/lightweight/heavyweight), GC age. Không lưu địa chỉ vì GC di chuyển object nhưng hashCode phải ổn định.

QVì sao int[] tốt hơn Integer[] trong hot path?+

int[] lưu 4B/phần tử liền mạch (cache-friendly). Integer[] lưu reference trỏ tới các Integer 16B rải rác → tốn RAM, nhiều cache miss, tăng áp lực GC.

Q== biên dịch thành bytecode nào cho reference vs int?+

Reference → if_acmpeq/if_acmpne (so con trỏ). int → if_icmpeq (so giá trị). .equals() → invokevirtual (dynamic dispatch, chạy code override).

QVì sao == trên String/Integer nguy hiểm dù đôi khi đúng?+

Có thể đúng do trùng string pool hoặc Integer cache → ảo giác code chạy được, rồi vỡ với dữ liệu ngoài pool/cache. Bug âm thầm. Luôn dùng .equals().

QInteger x = 100 compiler chèn gì?+

Integer.valueOf(100). valueOf khác new Integer vì dùng IntegerCache (-128..127) trả object chung. new Integer luôn tạo object mới (đã deprecated).

QVì sao Integer 127==127 true nhưng 128==128 false?+

IntegerCache cache -128..127 nên 127 trả cùng object. 128 ngoài cache → valueOf tạo 2 object khác nhau → == (so địa chỉ) false. Chỉnh được qua -XX:AutoBoxCacheMax.

Qint v = map.get(key) khi key không tồn tại?+

get trả null, autounbox gọi null.intValue() → NullPointerException. Bẫy với Map<_,Integer>. Dùng getOrDefault hoặc kiểm tra null.

QString immutability được thực thi thế nào?+

Field value (byte[] từ J9) là private final, không setter, không leak reference; class String là final. Nhờ đó thread-safe, cache hashCode, và pool tái dùng an toàn.

QString pool nằm ở đâu? Literal intern khi nào?+

Bảng hash trong heap (từ J7; trước ở PermGen). Literal intern tự động lúc class load qua bytecode ldc trỏ CONSTANT_String. new String() tạo object mới ngoài pool.

Qa + b trong vòng lặp vì sao O(n²)? Fix?+

Mỗi += biên dịch thành StringBuilder mới + toString mới (J8) hoặc invokedynamic (J9+), tạo object trung gian mỗi vòng. Dùng một StringBuilder ngoài loop → O(n).

QCompact Strings (Java 9) là gì?+

String dùng byte[] + coder (LATIN1 1B/char cho ASCII, UTF16 2B cho còn lại) thay char[] cố định 2B → tiết kiệm ~50% RAM cho text ASCII.

QStringBuilder vs StringBuffer?+

Cả hai mutable. StringBuffer synchronized (thread-safe, chậm hơn); StringBuilder không đồng bộ (nhanh, dùng 1 thread — phổ biến nhất). Nối chuỗi trong loop dùng StringBuilder.

QStatic dispatch vs dynamic dispatch?+

Overriding → dynamic dispatch: invokevirtual tra vtable của kiểu runtime lúc chạy. Overloading → static dispatch: chọn method lúc compile theo kiểu tĩnh tham số. invokeinterface tra itable.

QThứ tự khởi tạo class có kế thừa?+

static cha → static con (1 lần khi load); rồi mỗi new: instance init + field cha → ctor cha → instance init + field con → ctor con.

QGọi method bị override từ constructor lớp cha thấy gì?+

Dynamic dispatch gọi vào lớp con nhưng field lớp con CHƯA init → thấy giá trị mặc định (null/0). Anti-pattern nguy hiểm, tránh gọi overridable method trong constructor.

QDiamond problem với default method giải quyết thế nào?+

Implement 2 interface có default method cùng tên → class BẮT BUỘC override, chọn tường minh bằng A.super.method(). Quy tắc: class thắng interface, interface con thắng cha.

Qequals/hashCode contract và hệ quả vi phạm?+

a.equals(b) ⇒ a.hashCode()==b.hashCode() (ngược lại không bắt buộc). Vi phạm: HashMap tính bucket bằng hashCode, 2 object equals mà hashCode khác rơi bucket khác → get/contains sai.

QVì sao dùng số 31 trong hashCode?+

31 lẻ + nguyên tố → phân phối hash tốt, giảm collision. 31*i == (i<<5)-i nên JIT tối ưu bằng shift+subtract. Là quy ước từ String.hashCode.

QBẫy đối xứng equals khi kế thừa?+

Nếu lớp con thêm field vào equals, parent.equals(child) có thể true còn child.equals(parent) false → phá symmetric. Giải: composition thay kế thừa, hoặc record (final).

QPhần nào của exception đắt nhất?+

fillInStackTrace() chạy lúc tạo exception, duyệt toàn bộ stack. throw/catch bản thân rẻ. Không dùng exception cho control flow; hot exception tắt stack trace qua constructor super(msg, cause, false, false).

QSuppressed exception trong try-with-resources?+

Resource đóng theo thứ tự ngược khai báo. Nếu body ném exception VÀ close() cũng ném, exception của body là chính, exception của close gắn vào getSuppressed() (không mất).

QChecked vs unchecked, khi nào dùng gì?+

Checked (IOException) bị compiler ép handle/throws — lỗi phục hồi được, nhưng lan khắp signature. Unchecked (RuntimeException) — lỗi lập trình. Nhiều codebase (Spring) ưu tiên unchecked cho lỗi nghiệp vụ.
