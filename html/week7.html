System Design

Khung trả lời có cấu trúc, ước lượng quy mô, và các thiết kế kinh điển. Interviewer đánh giá cách bạn reason về trade-off, không phải đáp án đúng duy nhất.

i Overview & TL;DR

System design interview không có đáp án duy nhất. Điểm số đến từ: làm rõ yêu cầu, ước lượng hợp lý, kiến trúc mạch lạc, và giải thích trade-off ở mỗi quyết định ("dùng X vì..., đánh đổi là...").

TL;DR — quy trình 8 bước
  • Requirements (functional + non-functional) → đừng nhảy vào schema ngay.
  • Scale estimation: DAU, QPS, storage, bandwidth.
  • API design → Data model → High-level architecture.
  • Deep dive vào component quan trọng nhất.
  • Scaling + failure handling + observability.
  • Luôn nêu trade-off: SQL vs NoSQL, sync vs async, cache ở đâu.
  • Con số nhớ: 1 ngày ≈ 86400s ≈ 100K s; 1M user ≈ 10 QPS.

3 Design: URL Shortener

Kiến trúc — read-heavy (10:1), cache đóng vai trò then chốt

Write: sinh ID → Base62 (7 ký tự = 62⁷ ≈ 3.5 nghìn tỷ) → lưu DB. Read: cache hit → redirect (301/302); miss → DB → cache.

Quyết định chính

  • ID: counter+Base62 (tuần tự) hoặc snowflake (phân tán).
  • Hash: MD5 lấy 7 ký tự → check collision → retry.
  • DB: SQL đơn giản hoặc KV store cho scale.

301 vs 302

  • 301 permanent: browser cache, không hit server lại → nhanh, mất analytics.
  • 302 temporary: luôn hit server → theo dõi click được.

User trên Gateway 1 gửi tin cho user trên Gateway 2 → publish vào Redis channel → Gateway 2 subscribe → đẩy tới client. Ordering: sequence number per conversation.

Vì sao WebSocket

  • Kết nối 2 chiều, giữ liên tục.
  • Mỗi connection = 1 goroutine (Go nhẹ).
  • Buffered channel per connection (write queue).

Thách thức

  • Multi-device fan-out.
  • Offline messages: store & forward khi reconnect.
  • Backpressure: buffer đầy → drop/disconnect.
  • Hot room (triệu user) → shard.

State machine: CREATED → PROCESSING → SUCCEEDED/FAILED. Mọi write có idempotency key. Reconciliation đối chiếu record nội bộ với PSP hàng ngày.
Điểm then chốt cho payment
  • Exactly-once nghiệp vụ: idempotency key trên mọi thao tác ghi.
  • Double-entry bookkeeping: mỗi giao dịch có debit + credit → audit được.
  • Outbox để publish event tin cậy.
  • Reconciliation: đối chiếu với PSP, xử lý mismatch (PSP thành công nhưng local fail → mark succeeded; ngược lại → refund).
  • Distributed lock per payment để chặn xử lý song song cùng payment.

Database sharding — lưu ý

Shard key quyết định phân bố (user_id tốt, country lệch). Cross-shard query đắt (tránh hoặc dùng materialized view). ? Flashcards

Q5 phút đầu của system design interview làm gì?+

Làm rõ functional requirements (hệ thống làm gì), non-functional (scale, latency, availability), constraints (read/write ratio, data size), nêu và xác nhận giả định. KHÔNG nhảy vào schema/tech stack ngay.

QƯớc lượng nhanh: 10M DAU → QPS?+

10M user × 10 req/ngày = 100M req/ngày ÷ 100K giây ≈ 1000 QPS trung bình, peak ~5× = 5000 QPS. Storage: 1KB × 100M = 100GB/ngày ≈ 36TB/năm.

QURL shortener: sinh short ID thế nào?+

Counter/snowflake ID → Base62 encode (7 ký tự = 62⁷ ≈ 3.5 nghìn tỷ). Hoặc hash (MD5) lấy 7 ký tự → check collision → retry. Cache hot URLs ở Redis (90%+ hit vì read-heavy).

Q301 vs 302 cho URL shortener?+

301 permanent: browser cache, không hit server lại → nhanh nhưng mất analytics. 302 temporary: luôn hit server → theo dõi click. Chọn theo nhu cầu analytics.

QChat multi-server: user A (server 1) gửi user B (server 2)?+

Gateway 1 publish message vào Redis Pub/Sub channel của user B → Gateway 2 (đang subscribe) nhận → đẩy tới client B qua WebSocket. Hoặc consistent hashing (user luôn nối cùng server).

QChat: đảm bảo thứ tự tin nhắn?+

Sequence number per conversation (server sinh monotonic seq mỗi room). Client sort theo seq. Gap detection: seq nhảy → request tin nhắn thiếu.

QPayment: chống double charge?+

Idempotency key trên mọi write; state machine (CREATED→PROCESSING chỉ 1 lần); distributed lock per payment; check store trước khi xử lý (completed → trả cached). Double-entry ledger để audit.

QPayment reconciliation là gì?+

Job hàng ngày đối chiếu record nội bộ với PSP. Mismatch: PSP thành công nhưng local fail → mark succeeded; local succeeded nhưng PSP fail → refund; thiếu một bên → alert điều tra.

QSQL vs NoSQL — chọn thế nào?+

SQL: quan hệ phức tạp, ACID, transaction (users, orders, payments). NoSQL: scale ngang, write nhiều, schema mềm (messages, logs, analytics). Chọn theo access pattern và yêu cầu nhất quán, không theo trend.

QFlash sale: chống oversell?+

Pre-warm stock vào Redis; atomic DECR (nếu <0 → sold out, return ngay); chỉ tạo order cho user lấy được stock; TTL trên reservation (không thanh toán trong 10 phút → release). Queue để làm mượt spike.

QDatabase sharding — lưu ý gì?+

Shard key phân bố đều (user_id tốt, country lệch → hot shard). Cross-shard query đắt → tránh/materialized view. Resharding đau → virtual shard. Join across shard không làm được → denormalize hoặc join tầng app.

QCache đặt ở đâu?+

Browser → CDN → API Gateway → App/Redis → DB. Càng gần user càng nhanh, càng ít kiểm soát. CDN cho static + public API; Redis cho shared state, session, hot data; local cache cho hot key cực nóng.

QNotification system: các điểm cần nêu?+

Priority queue (urgent vs regular), rate limit per user/channel, template engine, deduplication, retry + DLQ, user preferences (opt-in/out per channel), tách API khỏi delivery bằng queue để chịu tải.
