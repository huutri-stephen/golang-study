Runtime + Performance

Cách Go cấp phát bộ nhớ, thu gom rác concurrent với STW cực ngắn, và cách đo lường/tối ưu bằng pprof + benchmark. Đây là phần phân biệt senior thật sự.

i Overview & TL;DR

Go đánh đổi một chút throughput để lấy độ trễ GC cực thấp (sub-millisecond STW) — phù hợp dịch vụ backend cần đuôi latency ổn định. Muốn tối ưu đúng: đo trước (pprof/benchmark), tìm hot path, rồi mới sửa.

TL;DR
  • Allocator theo tầng: mcache (per-P, không lock) → mcentral → mheap, chia object theo size class.
  • Object nhỏ (<32KB) đi qua size class; lớn cấp trực tiếp từ mheap.
  • Escape analysis quyết định stack/heap tại compile-time; kiểm tra -gcflags="-m".
  • GC: concurrent tri-color mark & sweep, chỉ 2 STW ngắn (~10–100µs).
  • Write barrier đảm bảo đúng đắn khi mark song song với chương trình.
  • GOGC (mặc định 100) điều khiển tần suất GC; Go 1.19+ có GOMEMLIMIT (soft limit).
  • pprof: CPU, heap (inuse/alloc), goroutine, mutex, block.
  • Benchmark: loop b.N, -benchmem, chặn dead-code elimination.
  • Tối ưu: pre-allocate, sync.Pool, tránh interface boxing, strings.Builder.

1 Memory Allocator

Go dùng allocator kiểu TCMalloc (thread-caching malloc), tối ưu cho môi trường nhiều goroutine.

Size class & tại sao giảm fragmentation

Go chia object nhỏ vào ~70 size class (8B, 16B, 32B, ...). Yêu cầu 20 bytes được làm tròn lên class 24B. Mỗi size class có span riêng chứa các object cùng kích thước → giảm phân mảnh ngoài (external fragmentation) và cho phép cấp phát/giải phóng O(1) trong span. Đánh đổi: phân mảnh trong (internal) nhẹ do làm tròn.

Loại objectĐường đi
Tiny (<16B, không chứa pointer)Gộp nhiều vào 1 block 16B (tiny allocator)
Small (16B–32KB)mcache → mcentral → mheap theo size class
Large (>32KB)Cấp trực tiếp từ mheap (span riêng)
Tại sao mcache per-P quan trọng

Vì gắn với P (không phải M hay G), cấp phát trong mcache không cần lock — chỉ một P truy cập tại một thời điểm. Đây là lý do cấp phát object nhỏ trong Go rất nhanh dù có hàng nghìn goroutine.

3 Garbage Collector

Triết lý GC của Go

Go chọn GC tối ưu cho độ trễ thấp và đơn giản hơn là throughput tối đa: non-generational, non-compacting, concurrent tri-color mark & sweep. Không generational (không chia young/old gen) để giữ runtime đơn giản — đánh đổi được chấp nhận vì đa số object Go chết trẻ nhưng escape analysis đã lọc nhiều object trên stack rồi.

Tri-color marking

Trắngchưa thăm · rác tiềm năng
Xámđã thăm, con chưa quét
Đenđã quét hết · reachable
Bắt đầu: tất cả TRẮNG · roots (stack, global) → XÁM
Lặp: lấy 1 XÁM → quét con → tô con XÁM → tô chính nó ĐENtới khi không còn object XÁM
Mọi TRẮNG còn lại = rác → sweep
Strong tri-color invariant: KHÔNG có object ĐEN nào trỏ trực tiếp tới object TRẮNG.

Các pha GC

Write Barrier — vì sao cần

Vấn đề khi mark song song

Trong lúc GC mark, chương trình (mutator) vẫn chạy và có thể sửa pointer. Kịch bản hỏng: object ĐEN mới trỏ tới object TRẮNG, đồng thời tham chiếu cũ tới object TRẮNG đó bị xóa → GC tưởng TRẮNG là rác → thu hồi nhầm object còn sống → memory corruption.

Không có write barrier — HỎNG

xóa trỏ C

STW trong Go ngắn cỡ nào

Từ Go 1.8+, STW pause thường < 1ms (thực tế ~10–100µs) nhờ marking concurrent + preemption bất đồng bộ (Go 1.14). Câu trả lời interview: "STW rất ngắn vì phần marking nặng chạy song song với chương trình; STW chỉ dành cho setup và termination."

Đặt GOMEMLIMIT ~ 90% RAM limit của container để tránh OOM-kill; kết hợp GOGC cao để giảm CPU. Trước 1.19, chỉ có GOGC nên dễ bị OOM khi burst allocation. Đây là câu hỏi thực tế cho backend chạy Kubernetes.

inuse vs alloc — phân biệt

inuse_space: đang chiếm bộ nhớ ngay bây giờ → dùng tìm leak (thứ đáng lẽ đã free mà chưa). alloc_space: tổng đã cấp từ đầu → dùng tìm allocation hotspot tạo GC pressure (dù đã free). Chọn sai profile → tìm nhầm vấn đề.

Bật mutex/block profile
runtime.SetMutexProfileFraction(1) // lấy mẫu tranh chấp mutex
runtime.SetBlockProfileRate(1)     // lấy mẫu blocking

Hai profile này tắt mặc định (có overhead). Bật khi nghi ngờ contention: CPU thấp nhưng throughput cũng thấp.

6 Benchmarking

func BenchmarkX(b *testing.B) {
    data := setup()      // setup không tính giờ
    b.ResetTimer()      // reset sau setup
    b.ReportAllocs()    // báo cáo allocation
    for i := 0; i < b.N; i++ {
        functionUnderTest(data)
    }
}

Bẫy: compiler tối ưu bỏ code
// SAI: compiler có thể loại bỏ vì kết quả không dùng
for i := 0; i < b.N; i++ { _ = compute() }

// ĐÚNG: gán vào biến package-level để chặn dead-code elimination
var sink int
func BenchmarkX(b *testing.B) {
    var r int
    for i := 0; i < b.N; i++ { r = compute() }
    sink = r
}
So sánh trước/sau bằng benchstat
go test -bench=. -count=10 > old.txt
# sửa code
go test -bench=. -count=10 > new.txt
benchstat old.txt new.txt   # cho p-value, khoảng tin cậy

Chạy nhiều lần (-count) để có ý nghĩa thống kê; một lần đo dễ nhiễu.

Pool giữ object tạm để tái dùng, giảm allocation trong hot path (vd buffer HTTP handler, JSON encoder). Lưu ý: object trong pool có thể bị GC thu hồi bất kỳ lúc nào (không phải cache bền); luôn reset trước khi Put. encoding/json, fmt dùng sync.Pool nội bộ.

? Flashcards

QKiến trúc allocator của Go?+

Ba tầng kiểu TCMalloc: mcache (per-P, không lock) → mcentral (theo size class, lock nhẹ) → mheap (toàn cục, xin OS qua mmap). Object nhỏ đi theo ~70 size class; lớn (>32KB) cấp trực tiếp từ mheap; tiny (<16B không pointer) gộp chung.

QVì sao cấp phát object nhỏ trong Go nhanh?+

mcache gắn với P nên cấp phát không cần lock (chỉ 1 P truy cập). Size class cho phép cấp/free O(1) trong span. Chỉ khi mcache hết span mới phải lock lên mcentral/mheap.

QGC của Go thuộc loại nào?+

Concurrent tri-color mark & sweep, non-generational, non-compacting. Tối ưu cho độ trễ thấp (STW ~10-100µs) hơn throughput. Marking chạy song song với chương trình, chỉ STW ở mark setup và mark termination.

QTri-color invariant là gì?+

Strong tri-color invariant: không object ĐEN nào trỏ trực tiếp tới object TRẮNG. Trắng=rác tiềm năng, Xám=đã thăm con chưa quét, Đen=đã quét hết. Kết thúc: mọi trắng còn lại là rác.

QWrite barrier giải quyết vấn đề gì?+

Khi mark chạy song song, chương trình sửa pointer có thể khiến object đen trỏ tới trắng đồng thời tham chiếu cũ bị xóa → GC thu hồi nhầm. Write barrier tô xám object liên quan khi ghi pointer → đảm bảo không mất object sống.

QGOGC=100 nghĩa là gì? GOMEMLIMIT?+

GOGC=100: GC kích hoạt khi heap tăng gấp đôi so với live heap sau GC trước. Thấp hơn → GC thường xuyên, ít RAM, tốn CPU. GOMEMLIMIT (1.19+): soft limit tổng bộ nhớ, GC tăng cường khi gần chạm → tránh OOM trong container.

QHeap profile inuse vs alloc?+

inuse_space: bộ nhớ đang sống → tìm leak. alloc_space: tổng đã cấp (kể cả đã free) → tìm allocation hotspot tạo GC pressure. Chọn sai → tìm nhầm vấn đề.

QCách viết benchmark chống compiler tối ưu?+

Gán kết quả vào biến package-level (sink) để chặn dead-code elimination. Dùng b.ResetTimer sau setup, b.ReportAllocs cho allocation. Chạy -count nhiều lần + benchstat để có ý nghĩa thống kê.

QOptimization workflow đúng?+

Baseline → tìm bottleneck (profile) → xác định hot path → tối ưu cụ thể → đo lại (benchstat) → validate production. Nguyên tắc: không bao giờ tối ưu khi chưa đo.

Qsync.Pool dùng khi nào và lưu ý gì?+

Tái dùng object tạm trong hot path (buffer, encoder) để giảm allocation. Lưu ý: object có thể bị GC thu hồi bất kỳ lúc nào (không phải cache bền), luôn reset trước Put. Không dùng cho object cần tồn tại lâu.

QVì sao fmt.Println gây allocation?+

Nhận ...interface{} → mọi tham số bị boxing → escape lên heap. Xuất hiện nhiều trong allocation profile. Trong hot path nên tránh fmt, dùng strconv/append trực tiếp.
