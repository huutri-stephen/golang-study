Distributed Systems

Khi hệ thống trải trên nhiều node và mạng: CAP, mô hình nhất quán, giao dịch phân tán (Saga, Outbox), idempotency, và các reliability pattern để chịu lỗi.

★★★★★Priority
9Chủ đề sâu
~14hĐề xuất

i Overview & TL;DR

Distributed systems là nơi câu hỏi interview chuyển từ "code thế nào" sang "reason về trade-off ra sao khi mạng lỗi". Nguyên lý xuyên suốt: mạng sẽ lỗi, node sẽ chết, message sẽ trùng/mất — thiết kế phải chấp nhận điều đó.

TL;DR
  • CAP: khi network partition (P bắt buộc), chọn C (từ chối request) hoặc A (trả data cũ).
  • Nhất quán: strong → eventual; read-after-write, causal là các mức trung gian.
  • 2PC blocking, không partition-tolerant; Saga = chuỗi local txn + compensation.
  • Outbox giải bài toán "ghi DB + publish event nguyên tử".
  • Idempotency key chống double-processing khi retry.
  • Retry phải kèm exponential backoff + jitter; chỉ retry lỗi transient.
  • Circuit breaker: Closed → Open → Half-Open, chặn cascading failure.
  • Rate limit: token bucket (cho phép burst) vs sliding window (chặt).
  • Compensation phải idempotent; distributed lock cần fencing token.

Hiểu đúng CAP

CAP chỉ nói về hành vi khi có partition. Lúc mạng bình thường, hệ thống có thể vừa consistent vừa available. Ngoài ra còn PACELC: nếu Partition thì chọn A/C, Else (bình thường) chọn Latency/Consistency — bổ sung góc nhìn latency.

Điểm yếu: nếu coordinator chết sau Prepare → participant khóa tài nguyên chờ mãi (blocking). Đồng bộ, không partition-tolerant.

Saga Pattern

Lỗi ở bước 3 → chạy compensation NGƯỢC chiều: Refund → Cancel. Compensation phải idempotent.

Choreography (event-driven)

  • Service phát/nghe event, tự phản ứng.
  • Loose coupling, không single point of failure.
  • Khó trace luồng, dependency ngầm.

Orchestration (coordinator)

  • Một orchestrator điều phối các bước.
  • Dễ hiểu, xử lý lỗi tập trung.
  • Orchestrator là single point of failure.
Chọn 2PC hay Saga

2PC: strong consistency, dùng khi cùng một DB nhiều bảng, hoặc hệ thống nhỏ chấp nhận blocking. Saga: eventual consistency, dùng cho microservices có DB riêng. Luồng >3 bước → orchestration; luồng đơn giản → choreography.

4 Outbox Pattern & CDC

Vấn đề: dual write không nguyên tử

Cần "update DB" VÀ "publish event" cùng lúc. Nhưng DB commit và Kafka publish là hai hệ thống khác nhau — không có transaction chung. Nếu DB commit xong rồi publish lỗi → event mất; nếu publish xong rồi DB rollback → event ma.

Outbox: ghi thay đổi + event vào CÙNG một DB transaction
1 DB Transaction (nguyên tử)
UPDATE orders SET status='paid'
INSERT INTO outbox (event)
Relay / CDCđọc bảng outbox
Kafka
mark published
Vì DB change + event nằm chung 1 transaction → nếu DB commit thì event CHẮC CHẮN sẽ được publish (relay retry tới khi thành công). At-least-once → consumer cần idempotent.
CDC (Change Data Capture)

Thay vì poll bảng outbox, đọc trực tiếp transaction log của DB (WAL PostgreSQL / binlog MySQL) và stream thay đổi ra message queue. Công cụ: Debezium, Maxwell. Ưu điểm: không cần sửa code ứng dụng, độ trễ thấp. Có thể thay hoàn toàn outbox hoặc kết hợp (đọc outbox qua CDC).

6 Retry & Exponential Backoff

Exponential backoff + jitter (base=100ms)
try 1ngay
try 2~100ms + jitter
try 3~200ms + jitter
try 4~400ms + jitter
… cap ở maxDelay
Delay nhân đôi mỗi lần → giảm áp lực; jitter (ngẫu nhiên) → tránh thundering herd khi nhiều client cùng retry.

NÊN retry (transient)

  • 5xx server error
  • Timeout, network error
  • 429 (theo Retry-After)
  • Connection reset

KHÔNG retry

  • 4xx client error (400, 401, 403)
  • 409 Conflict (state không đổi)
  • Non-idempotent không có key
  • Circuit breaker đang Open
Vì sao cần jitter

Không jitter: 100 client cùng timeout lúc t → cùng retry lúc t+1s → dội server lần nữa → lại timeout → chu kỳ lặp (retry storm). Jitter phân tán thời điểm retry ngẫu nhiên, phá đồng bộ hóa.

7 Circuit Breaker

Máy trạng thái 3 pha — chặn cascading failure
CLOSEDbình thường, đếm lỗi
lỗi > ngưỡng ↓
OPENfail nhanh, không gọi downstream
sau timeout ↓
HALF-OPENthử 1 request
HALF-OPEN → thành công → CLOSED HALF-OPEN → lỗi → OPEN
Vì sao dùng circuit breaker

Khi downstream chết, mọi request đều timeout → goroutine dồn ứ, tài nguyên cạn, lỗi lan ngược lên (cascading failure). Circuit breaker fail nhanh (Open) thay vì chờ timeout, cho downstream thời gian hồi phục, và tự thăm dò (Half-Open). Kết hợp với fallback/graceful degradation.

Bulkhead — cô lập lỗi

Như vách ngăn tàu thủy: chia tài nguyên (connection pool, goroutine) thành ngăn riêng cho từng dependency. Nếu service A cạn pool của nó, service B vẫn hoạt động. Ngăn một dependency chậm làm sập toàn bộ.

Distributed lock — điểm yếu

Lock dựa TTL có rủi ro: clock skew, GC pause khiến holder tưởng còn giữ lock nhưng đã hết hạn → hai client cùng vào critical section. Giải pháp chặt: fencing token — token tăng dần, storage từ chối token cũ hơn token đã thấy.

QCAP theorem — giải thích thực tế.+

Hệ phân tán chỉ giữ 2/3: Consistency, Availability, Partition tolerance. Vì mạng luôn có thể partition (P bắt buộc), thực chất chọn: CP (từ chối request để giữ nhất quán) hay AP (trả data cũ để giữ khả dụng). "CA" chỉ có ở hệ một node.

QEventual consistency chấp nhận khi nào?+

Khi business chịu được data cũ tạm thời và user không nhận ra: feed, analytics, đếm view, recommendation. KHÔNG chấp nhận: tiền, tồn kho, authentication.

Q2PC có vấn đề gì?+

Blocking: coordinator chết sau Prepare → participant khóa tài nguyên chờ mãi. Đồng bộ (mọi participant phải sẵn sàng), single point of failure, không partition-tolerant. Thay bằng Saga cho microservices.

QSaga: choreography vs orchestration?+

Choreography: service phát/nghe event, loose coupling, không SPOF, nhưng khó trace. Orchestration: coordinator điều phối, dễ hiểu, xử lý lỗi tập trung, nhưng orchestrator là SPOF. Luồng >3 bước → orchestration.

QPayment thành công nhưng Inventory lỗi — recover thế nào?+

Saga compensation: Inventory phát event thất bại → Payment nghe → Refund → Order nghe → Cancel. Chạy compensation ngược chiều các bước đã hoàn tất. Compensation phải idempotent.

QOutbox pattern giải quyết gì?+

Dual write không nguyên tử: update DB + publish event là 2 hệ thống, không có transaction chung. Outbox: ghi DB change + event vào cùng 1 DB transaction; relay/CDC đọc outbox rồi publish. Nếu DB commit → event chắc chắn được publish (at-least-once).

QCDC là gì?+

Change Data Capture: đọc transaction log của DB (WAL/binlog) và stream thay đổi ra message queue. Công cụ Debezium/Maxwell. Không cần sửa code app, độ trễ thấp. Có thể thay hoặc kết hợp outbox.

QChống double charge khi retry?+

Idempotency key: client gửi key duy nhất; server check store → completed trả cached, processing trả 409, chưa có thì lock + xử lý + lưu. Consumer idempotent: lưu message ID + business logic trong cùng transaction, skip nếu ID đã xử lý.

QVì sao retry cần jitter?+

Không jitter: nhiều client cùng timeout → cùng retry một lúc → dội server lần nữa (retry storm/thundering herd). Jitter thêm ngẫu nhiên vào delay → phân tán thời điểm retry, phá đồng bộ hóa.

QKhi nào KHÔNG nên retry?+

4xx (400/401/403 — sẽ lỗi lại), 409 Conflict (state không đổi), thao tác non-idempotent không có key, circuit breaker đang Open. Chỉ retry lỗi transient: 5xx, timeout, network error, 429 (theo Retry-After).

QCircuit breaker — 3 trạng thái?+

Closed (bình thường, đếm lỗi; vượt ngưỡng → Open). Open (fail nhanh, không gọi downstream; sau timeout → Half-Open). Half-Open (thử 1 request; thành công → Closed, lỗi → Open). Chặn cascading failure, cho downstream hồi phục.

QToken bucket vs sliding window?+

Token bucket: token nạp đều, request lấy 1 token, cho phép burst tới size bucket, ít bộ nhớ. Sliding window: đếm request trong cửa sổ trượt, chính xác, không cho burst, tốn bộ nhớ hơn. Bucket cho API cho phép spike; sliding cho enforce chặt.

QDistributed rate limit race condition — fix?+

Nhiều instance check+increment không nguyên tử → cùng đọc 99, cùng tăng → vượt limit. Fix: Redis Lua script (check+increment atomic) hoặc INCR+EXPIRE trong MULTI/EXEC.

QDistributed lock có điểm yếu gì?+

Lock TTL: clock skew, GC pause khiến holder tưởng còn giữ nhưng đã hết hạn → 2 client cùng vào critical section. Fix chặt: fencing token — token tăng dần, storage từ chối token cũ hơn token đã thấy.

QBulkhead pattern?+

Như vách ngăn tàu thủy: chia tài nguyên (pool, goroutine) thành ngăn riêng cho từng dependency. Một dependency cạn pool riêng thì không ảnh hưởng dependency khác → ngăn cascading failure.
