Range scan (WHERE x BETWEEN…) đi dọc chuỗi leaf liên kết → hiệu quả.
Vì sao B-Tree, không phải binary tree hay hash?
  • Branching factor lớn: mỗi node = 1 page (~4-16KB) chứa nhiều key → cây nông (3-4 level cho hàng triệu row) → ít disk I/O. Binary tree quá sâu → nhiều lần đọc disk.
  • Sorted + leaf liên kết: hỗ trợ range query và ORDER BY. Hash index O(1) cho equality nhưng KHÔNG làm được range.

Composite Index — Leftmost Prefix Rule

Index (user_id, status, created_at) — sorted như từ điển
DÙNG ĐƯỢC
WHERE user_id=1 (cột 1)
DÙNG ĐƯỢC
… AND status='active' (cột 1,2)
DÙNG ĐƯỢC
… AND created_at > '…' (cả 3)
KHÔNG DÙNG
WHERE status='active' (bỏ cột 1)
KHÔNG DÙNG

user_id=1 AND created_at>'…' (chỉ cột 1, cột 3 lọc sau)
Không tra được từ điển nếu không biết chữ cái đầu → phải có cột trái nhất.

Index-Only Scan

Nếu index chứa tất cả cột mà query cần (SELECT + WHERE), DB đọc dữ liệu thẳng từ index, không cần truy cập bảng (index-only scan) → nhanh nhất. Ngược lại phải "index scan + table lookup" cho mỗi row khớp.

2 Transaction & Isolation

ACID: Atomicity (all-or-nothing), Consistency (valid→valid), Isolation (không giẫm chân nhau), Durability (committed=bền).

Isolation LevelDirty ReadNon-repeatable ReadPhantom Read
Read Uncommittedcócócó
Read Committed (PG default)khôngcócó
Repeatable Read (MySQL default)khôngkhôngcó*
Serializablekhôngkhôngkhông

Ba hiện tượng đọc
  • Dirty Read: đọc dữ liệu của transaction khác CHƯA commit (có thể bị rollback).
  • Non-repeatable Read: đọc cùng 1 row hai lần, giá trị khác (row bị update giữa chừng).
  • Phantom Read: chạy cùng query hai lần, số row khác (row mới được insert).
Chọn isolation level

Cao hơn = an toàn hơn nhưng chậm hơn (nhiều lock/abort). Mặc định Read Committed đủ cho hầu hết. Dùng Serializable cho thao tác tài chính nhạy cảm; xử lý được lỗi serialization (retry). Transfer tiền: Repeatable Read + SELECT FOR UPDATE.

3 MVCC & Locking

Vấn đề MVCC giải quyết

Không có MVCC, reader và writer tranh nhau lock → đọc bị chặn bởi ghi và ngược lại → throughput thấp. MVCC (Multi-Version Concurrency Control) cho phép reader không chặn writer, writer không chặn reader.

MVCC: mỗi row nhiều phiên bản, đọc theo snapshot
T1 bắt đầusnapshot @ t1
Row X = "A" (version @ t0)
T2 UPDATE X="B"
tạo version MỚI @ t2KHÔNG ghi đè bản cũ
T1 đọc X
vẫn thấy "A"snapshot t1 < t2 · không bị chặn
T2 commit
T1 vẫn thấy "A"tới khi T1 kết thúc (Repeatable Read)
Version cũ được dọn bởi VACUUM (PostgreSQL) khi không transaction nào còn cần.

Optimistic vs Pessimistic locking
  • Pessimistic (SELECT ... FOR UPDATE): khóa row ngay khi đọc. Dùng khi tranh chấp cao.
  • Optimistic (version column): không khóa, kiểm tra version lúc update; nếu đổi → retry. Dùng khi tranh chấp thấp, throughput cao.

4 Connection Pool & N+1 Query

Vì sao cần connection pool

Mỗi kết nối DB tốn TCP handshake (~1-3ms) + TLS + auth. Không pool → mỗi query trả giá này. Pool tái dùng connection sẵn có → giảm latency đáng kể.

db.SetMaxOpenConns(25)               // tối đa connection active
db.SetMaxIdleConns(10)               // giữ sẵn để tái dùng
db.SetConnMaxLifetime(5 * time.Minute) // recycle định kỳ
db.SetConnMaxIdleTime(1 * time.Minute) // đóng idle lâu
Sizing pool

Quá ít → request xếp hàng chờ connection → latency tăng. Quá nhiều → vượt max_connections của DB, tốn RAM/context-switch phía DB → chậm cả hệ thống. Công thức khởi điểm: (CPU cores × 2) + spindles; thực tế 10-25, rồi đo wait duration và active count để tinh chỉnh. Nhớ: nhiều app instance × pool size = tổng connection tới DB.

N+1 Query Problem

SAI · N+1 query
SELECT * FROM users1 query
mỗi user: SELECT orders WHERE user_id=?N query
100 user = 101 query!
ĐÚNG · JOIN / batch
JOIN users + orders1 query
— hoặc —
SELECT orders WHERE user_id IN (…)1 batch query
Khắc phục N+1

JOIN, batch với IN (...), hoặc DataLoader pattern (gom key rồi query 1 lần). ORM thường ẩn N+1 — bật query logging để phát hiện. Đây là nguyên nhân latency phổ biến nhất khi API chậm.

Vì sao Redis nhanh dù single-threaded

Redis xử lý command trên một luồng chính (đến 6.x) → không cần lock, không race, mọi command atomic. Nhanh nhờ: toàn bộ dữ liệu trong RAM, cấu trúc dữ liệu tối ưu, I/O multiplexing (epoll). Đơn luồng cũng là lý do command O(n) nặng (vd KEYS *) chặn cả server — tránh trong production.

Redis vs Memcached

Redis: cấu trúc dữ liệu phong phú, persistence (RDB/AOF), pub/sub, cluster native. Memcached: chỉ string, đa luồng, tiết kiệm bộ nhớ hơn cho pure cache. Chọn Redis khi cần hơn cache đơn thuần.

Singleflight — chống stampede

Khi nhiều goroutine cùng miss một key, chỉ một goroutine thực sự query DB; các goroutine khác chờ và dùng chung kết quả. Go có package golang.org/x/sync/singleflight. Đây là câu trả lời chuẩn cho câu hỏi cache stampede.

// NX = chỉ set nếu chưa tồn tại (acquire)

Lưu ý: distributed lock có điểm yếu (clock skew, GC pause khiến lock hết hạn sớm). Với yêu cầu chặt cần fencing token.

9 Go Database Access

sql.DB là POOL, không phải 1 connection

sql.Open không kết nối ngay — chỉ tạo pool (lazy). Cần PingContext để kiểm tra kết nối thật. Cấu hình pool: SetMaxOpenConns, SetMaxIdleConns, SetConnMaxLifetime (tái tạo connection cũ tránh bị LB/DB đóng ngầm).

Placeholder chống SQL injection
db.QueryRowContext(ctx, `SELECT id FROM users WHERE id = $1`, id)  // driver escape
// KHÔNG BAO GIỜ: "... WHERE id = " + userInput  → lỗ hổng SQLi
Query nhiều dòng — phải Close + Err
rows, err := db.QueryContext(ctx, q, args...)
if err != nil { return err }
defer rows.Close()          // BẮT BUỘC: trả connection về pool
for rows.Next() {
    rows.Scan(&u.ID, &u.Email)
}
return rows.Err()          // lỗi phát sinh giữa chừng
Transaction an toàn — defer Rollback
tx, _ := db.BeginTx(ctx, opts)
defer tx.Rollback()   // Commit OK → no-op; return sớm → tự rollback (không leak tx)
tx.ExecContext(ctx, `UPDATE ... balance-$1`, amt, from)
tx.ExecContext(ctx, `UPDATE ... balance+$1`, amt, to)
return tx.Commit()

Map sql.ErrNoRows sang lỗi domain bằng errors.Is(err, sql.ErrNoRows).

? Flashcards

QVì sao DB dùng B-Tree, không phải binary tree hay hash?+

B-Tree branching factor lớn (mỗi node = 1 page nhiều key) → cây nông → ít disk I/O. Binary tree quá sâu → nhiều disk read. Hash O(1) equality nhưng không làm được range query; B-Tree sorted + leaf liên kết hỗ trợ range và ORDER BY.

QLeftmost prefix rule của composite index?+

Index (A,B,C) dùng được cho WHERE bắt đầu từ A: A / A,B / A,B,C. KHÔNG dùng được nếu bỏ A (chỉ B, hoặc chỉ C). Vì index sorted theo (A,B,C) như từ điển — cần biết cột đầu.

QCovering index / index-only scan?+

Index chứa tất cả cột query cần (SELECT+WHERE) → đọc thẳng từ index, không truy cập bảng → nhanh nhất. Ngược lại phải index scan + table lookup mỗi row.

QMVCC hoạt động thế nào?+

Mỗi row có nhiều version. Transaction đọc theo snapshot → thấy version phù hợp thời điểm bắt đầu. Writer tạo version mới, không ghi đè → reader không chặn writer và ngược lại. Version cũ dọn bởi VACUUM (PG).

QDirty / Non-repeatable / Phantom read?+

Dirty: đọc data chưa commit. Non-repeatable: đọc cùng row 2 lần giá trị khác (bị update). Phantom: cùng query 2 lần số row khác (bị insert). Read Committed chặn dirty; Repeatable Read chặn non-repeatable; Serializable chặn hết.

QConnection pool: quá ít vs quá nhiều?+

Quá ít → request xếp hàng chờ connection → latency. Quá nhiều → vượt max_connections DB, tốn RAM/context-switch phía DB → chậm cả hệ thống. Nhớ: nhiều app instance × pool = tổng connection tới DB.

QN+1 query và cách fix?+

1 query list + N query con (mỗi item 1 query) → 100 item = 101 query. Fix: JOIN, batch IN(...), hoặc DataLoader. ORM thường ẩn N+1 — bật query log để phát hiện. Nguyên nhân latency phổ biến nhất.

QVì sao write invalidate cache thay vì update?+

Update cache khi write dễ race: 2 write đồng thời ghi cache khác thứ tự DB → cache sai vĩnh viễn. Invalidate (xóa) an toàn hơn: lần đọc sau nạp giá trị mới nhất từ DB.

QCache stampede và cách xử lý?+

Hot key hết hạn → nhiều request cùng miss → dồn vào DB → quá tải. Xử lý: singleflight (1 request nạp, còn lại chờ dùng chung kết quả), refresh sớm trước khi hết hạn, hoặc never-expire + background refresh.

QCache penetration vs avalanche?+

Penetration: query key không tồn tại trong DB → luôn miss → bào mòn DB. Fix: cache null value (TTL ngắn), bloom filter. Avalanche: nhiều key hết hạn cùng lúc → spike DB. Fix: TTL + jitter ngẫu nhiên.

QKafka ordering guarantee?+

Chỉ đảm bảo thứ tự TRONG một partition. Cùng key → cùng partition → có thứ tự. Khác key → khác partition → song song, không đảm bảo thứ tự tổng. Muốn order theo entity → dùng entity ID làm key.

QAt-least-once vs exactly-once? Cách thực dụng?+

At-least-once: commit offset SAU xử lý → không mất, có thể trùng. Exactly-once: phức tạp/tốn kém. Thực dụng: at-least-once + consumer idempotent (lưu message ID, skip trùng) → hiệu ứng exactly-once về nghiệp vụ mà đơn giản.

QVì sao Redis nhanh dù single-threaded? Hệ quả?+

Một luồng → không lock, mọi command atomic. Nhanh nhờ in-memory + cấu trúc tối ưu + epoll. Hệ quả: command O(n) nặng (KEYS *) chặn cả server → tránh trong production, dùng SCAN thay thế.

Qsql.DB là 1 connection hay pool?+

Là POOL (safe cho concurrent). sql.Open không kết nối ngay (lazy) — cần PingContext để kiểm tra thật. Cấu hình SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime. Không cần tự pool thêm.

QPattern transaction an toàn trong Go?+

BeginTx rồi defer tx.Rollback() ngay. Commit thành công thì Rollback là no-op; return sớm vì lỗi thì tự rollback → không bao giờ leak tx/connection.

QChống SQL injection trong Go?+

Luôn dùng placeholder ($1 Postgres, ? MySQL) — driver tự escape. KHÔNG BAO GIỜ nối chuỗi input vào query. Ngoài ra defer rows.Close() và kiểm tra rows.Err() để tránh leak/bỏ sót lỗi.

Qsqlx/sqlc vs GORM — chọn thế nào?+

sqlx/sqlc: SQL tường minh, kiểm soát hiệu năng, sqlc type-safe không reflection. GORM: nhanh viết CRUD nhưng reflection (chậm), query sinh tự động khó tối ưu, dễ N+1. Hot path → ưu tiên SQL tường minh.
