i Overview & TL;DR

Viết được HTTP handler thì dễ; viết dịch vụ không sập dưới tải, không leak connection, shutdown sạch, và trả lỗi đúng chuẩn mới là senior. Trọng tâm tuần này là những chi tiết production thường bị bỏ qua.

TL;DR
  • HTTP/2 giải quyết head-of-line blocking của HTTP/1.1 bằng multiplexing streams.
  • http.Transport tự pool connection — nhưng phải resp.Body.Close() nếu không leak.
  • Set đầy đủ timeout: dial, TLS, response header, idle, và tổng.
  • Server: ReadTimeout, WriteTimeout, IdleTimeout để chống slowloris và stuck handler.
  • Middleware = func(http.Handler) http.Handler, chain theo thứ tự.
  • Graceful shutdown: ngừng nhận mới → drain in-flight → cleanup.
  • Context: tham số đầu, không lưu trong struct, always defer cancel.
  • Idempotency key để chống double-charge khi client retry.

Head-of-line blocking

Trên HTTP/1.1, mỗi TCP connection xử lý request tuần tự — request B phải chờ response A xong (dù A chậm). Trình duyệt mở nhiều connection để lách. HTTP/2 multiplexing nhiều "stream" trên một connection → không chờ nhau ở tầng HTTP. Nhưng vẫn còn HOL ở tầng TCP (mất 1 packet chặn cả connection) → HTTP/3 dùng QUIC/UDP để giải quyết triệt để.

Keep-Alive vì sao quan trọng

Mỗi connection mới tốn TCP handshake + TLS (~vài ms–chục ms). Keep-Alive tái dùng connection cho nhiều request → tiết kiệm hầu hết chi phí thiết lập. Go client/server bật keep-alive mặc định. Đây là nền tảng của connection pooling.

2 HTTP Client & Connection Pool

Đừng dùng http.Get / DefaultClient trong production

http.Get và http.DefaultClient không có timeout → một downstream chậm có thể treo goroutine vô hạn, dồn ứ → cạn tài nguyên. Luôn tạo client với timeout rõ ràng.

client := &http.Client{
    Timeout: 30 * time.Second,        // tổng deadline
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   5 * time.Second,   // timeout kết nối TCP
            KeepAlive: 30 * time.Second,
        }).DialContext,
        TLSHandshakeTimeout:   5 * time.Second,
        ResponseHeaderTimeout: 10 * time.Second,
        MaxIdleConns:          100,   // tổng idle
        MaxIdleConnsPerHost:   10,    // idle mỗi host
        MaxConnsPerHost:       50,    // tối đa mỗi host
        IdleConnTimeout:       90 * time.Second,
    },
}

3 HTTP Server

srv := &http.Server{
    Addr:           ":8080",
    Handler:        mux,
    ReadTimeout:    5 * time.Second,   // chống slowloris
    WriteTimeout:   10 * time.Second,  // chống handler treo
    IdleTimeout:    120 * time.Second, // đóng keep-alive idle
    MaxHeaderBytes: 1 << 20,          // giới hạn header 1MB
}
Vì sao mỗi timeout tồn tại
  • ReadTimeout: chống slowloris attack — kẻ tấn công gửi request cực chậm để giữ connection, làm cạn thread/goroutine.
  • WriteTimeout: chống handler ghi response quá lâu (client chậm hoặc handler kẹt).
  • IdleTimeout: đóng keep-alive connection không dùng, giải phóng tài nguyên.
Cơ chế: goroutine mỗi connection

Go server spawn một goroutine cho mỗi connection (accept loop). Nhờ goroutine rẻ, model này scale tốt tới hàng chục nghìn connection. Nhưng handler chậm/leak sẽ tích lũy goroutine → đây là lý do cần timeout và giám sát NumGoroutine.

Bảo mật

Endpoint mạng nên có auth/rate-limit. Server không giới hạn body size dễ bị tấn công memory — dùng http.MaxBytesReader. Không log dữ liệu nhạy cảm (token, mật khẩu).

4 Middleware Pattern

type Middleware func(http.Handler) http.Handler

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)          // gọi handler tiếp theo
        log.Printf("%s %v", r.URL.Path, time.Since(start))
    })
}

Thứ tự middleware hợp lý

Ngoài → trong: RequestID → Recovery → Logging → CORS → RateLimit → Auth → Handler. Recovery đặt ngoài để bắt panic của mọi tầng trong. RequestID đặt ngoài cùng để mọi log đều có trace ID. Auth đặt sát handler để chỉ chạy sau khi qua các lớp bảo vệ chung.

Wrap ResponseWriter để bắt status code

Handler gọi WriteHeader(200) nhưng middleware không "thấy" status để log. Giải pháp: bọc http.ResponseWriter trong struct riêng, override WriteHeader/Write để lưu status và size, rồi log sau khi handler xong.

K8s: SIGTERM → preStop hook → chờ terminationGracePeriodSeconds → SIGKILL nếu chưa xong. Đặt shutdown timeout < grace period (mặc định 30s).
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
srv.Shutdown(ctx)  // graceful: drain rồi đóng
Shutdown vs Close

srv.Shutdown(ctx): graceful — chờ request đang chạy xong (tới khi ctx hết hạn). srv.Close(): đóng ngay, cắt mọi connection đang xử lý → mất request. Production luôn dùng Shutdown.

6 Context

Ba mục đích của context
  • Cancellation: lan truyền tín hiệu hủy xuống toàn cây gọi.
  • Deadline/Timeout: tự động hủy sau thời hạn.
  • Request-scoped values: trace ID, user ID (KHÔNG phải tham số hàm).

ctx.Done() đóng khi: hết 5s / gọi cancel() / cha bị hủy → mọi tầng đang chờ <-ctx.Done() được đánh thức để dừng.
Tại sao KHÔNG lưu context trong struct

Context có vòng đời một request (ngắn). Struct thường sống lâu hơn (cả vòng đời app). Lưu context vào struct tạo lệch vòng đời: tín hiệu hủy lỗi thời, rò rỉ, propagation sai. Luôn truyền context làm tham số đầu tiên: func Do(ctx context.Context, ...).

Best practices
  • Tham số đầu tiên; không truyền nil (dùng context.Background()/TODO()).
  • Luôn defer cancel() để tránh leak context.
  • Key dùng type unexported để tránh va chạm: type ctxKey string.
  • Values chỉ cho dữ liệu request-scoped (trace ID), KHÔNG cho DB/logger/config.
  • Kiểm tra <-ctx.Done() trong vòng lặp dài và mọi thao tác blocking.
  • Propagate xuống downstream: db.QueryContext(ctx,...), req.WithContext(ctx).

Pagination: Offset vs Cursor

Offset (?page=2&size=20)

  • Đơn giản, nhảy trang bất kỳ.
  • Chậm với offset lớn (DB phải quét bỏ).
  • Không nhất quán khi insert/delete (skip/duplicate).

Cursor (?cursor=xxx&limit=20)

  • Hiệu năng ổn định O(1) (dùng index).
  • Nhất quán khi dữ liệu thay đổi.
  • Không nhảy trang tùy ý; phức tạp hơn.

9 gRPC & Protobuf

Protobuf — binary + schema

IDL + binary serialization của Google. Nhỏ & nhanh hơn JSON, có schema. Định nghĩa .proto → sinh code Go bằng protoc. Field number là hợp đồng trên wire — không đổi/không tái dùng; thêm field mới với number mới → backward compatible.

4 kiểu RPC

  • Unary: 1 req → 1 resp
  • Server streaming: 1 → nhiều
  • Client streaming: nhiều → 1
  • Bidi streaming: nhiều ↔ nhiều (chat)

Interceptor (≈ middleware)

Dùng cho auth, logging, metrics, tracing (OTel), recovery, rate limit. grpc.ChainUnaryInterceptor(...).

10 Security · Authentication & Authorization

AuthN vs AuthZ

Authentication = "Bạn là ai?" (verify danh tính). Authorization = "Bạn được làm gì?" (kiểm tra quyền). Nhắc lại: 401 chưa/không xác thực; 403 xác thực rồi nhưng không đủ quyền.

JWT — stateless token
header.payload.signature   // base64url, chỉ KÝ chứ không mã hoá
  • Server không lưu session → verify bằng chữ ký → scale ngang tốt.
  • Payload ai cũng đọc được → KHÔNG để dữ liệu nhạy cảm.
  • HS256 (HMAC, secret chung) vs RS256 (RSA, private ký / public verify — nhiều service).
  • Khó revoke trước hạn → TTL ngắn + refresh token (lưu server, revoke được).
Bẫy bảo mật thường gặp
  • Verify JWT phải kiểm tra signing method (chống thuật toán "none"/confusion).
  • Băm mật khẩu bằng bcrypt/argon2 (có salt, chậm có chủ đích) — KHÔNG MD5/SHA-256 trần.
  • So sánh token/HMAC bằng hmac.Equal / subtle.ConstantTimeCompare (chống timing attack).
  • Giới hạn body (http.MaxBytesReader), parameterized query (chống SQLi), CORS đúng origin.
OAuth2 / OIDC

OAuth2 = ủy quyền truy cập; OIDC = lớp authentication trên OAuth2 (thêm ID token). Flow phổ biến: Authorization Code + PKCE (web/mobile), Client Credentials (service-to-service). Đừng tự viết OAuth server — dùng provider (Keycloak/Auth0/Cognito).

? Flashcards

QHTTP/1.1 head-of-line blocking là gì? HTTP/2 giải quyết ra sao?+

Trên 1 TCP connection HTTP/1.1, request xử lý tuần tự — B chờ A xong dù A chậm. HTTP/2 multiplexing nhiều stream trên 1 connection → không chờ nhau ở tầng HTTP. Vẫn còn HOL ở tầng TCP → HTTP/3 dùng QUIC/UDP.

QVì sao phải đóng response body?+

Không đóng → connection không trả về pool → leak. Pool cạn dần → request mới timeout, nhiều TCP TIME_WAIT. Luôn defer resp.Body.Close() và đọc hết body (io.Copy vào io.Discard) để tái dùng connection.

QVì sao không dùng http.DefaultClient trong production?+

Không có timeout → downstream chậm treo goroutine vô hạn, dồn ứ, cạn tài nguyên. Luôn tạo client với Timeout + Transport cấu hình pool và các timeout con.

QCác server timeout và mục đích?+

ReadTimeout: chống slowloris (gửi request cực chậm giữ connection). WriteTimeout: chống handler ghi response quá lâu. IdleTimeout: đóng keep-alive idle. MaxHeaderBytes: giới hạn header.

QThứ tự middleware hợp lý và vì sao Recovery đặt ngoài?+

RequestID → Recovery → Logging → CORS → RateLimit → Auth → Handler. Recovery ngoài để bắt panic của mọi tầng trong. RequestID ngoài cùng để mọi log có trace ID. Middleware ngoài chạy đầu tiên lúc vào, cuối cùng lúc ra.

QGraceful shutdown flow trong Kubernetes?+

SIGTERM → health check trả 503 → srv.Shutdown(ctx) ngừng nhận mới, drain in-flight → cleanup (DB, metrics) → exit. Đặt shutdown timeout < terminationGracePeriodSeconds (mặc định 30s) để tránh SIGKILL.

QVì sao không lưu context trong struct?+

Context có vòng đời một request (ngắn); struct sống lâu hơn → lệch vòng đời, tín hiệu hủy lỗi thời, rò rỉ, propagation sai. Luôn truyền làm tham số đầu tiên.

Q401 vs 403?+

401 Unauthorized: chưa biết bạn là ai (thiếu/sai token). 403 Forbidden: biết rồi nhưng không đủ quyền. "Who are you?" vs "I know you, but no."

QOffset vs cursor pagination?+

Offset: đơn giản, nhảy trang bất kỳ, nhưng chậm với offset lớn và không nhất quán khi insert/delete. Cursor: O(1) ổn định (dùng index), nhất quán, nhưng không nhảy trang tùy ý. User-facing feed → cursor.

QIdempotency key chống double charge thế nào?+

Client gửi key duy nhất. Server: key completed → trả cached response; processing → 409; chưa có → lock, xử lý, lưu response. Lỗi → xóa key cho retry. Store Redis/DB với TTL 24-48h + distributed lock.

QTriệu chứng và fix connection pool exhaustion?+

Triệu chứng: latency tăng dần, TCP TIME_WAIT nhiều, connection refused/timeout. Fix: đóng response body (nguyên nhân #1), tăng MaxConnsPerHost, set IdleConnTimeout, sửa downstream chậm (giữ connection lâu).

QgRPC vs REST — khi nào dùng cái nào?+

gRPC: internal service-to-service, low latency, cần streaming — payload protobuf binary trên HTTP/2. REST/JSON: public API, browser-facing, đơn giản. gRPC cần grpc-web/proxy cho browser.

QVì sao không đổi/tái dùng protobuf field number?+

Field number là định danh trên wire (hợp đồng). Đổi/tái dùng sẽ phá backward compatibility. Thêm field mới với number mới thì vẫn tương thích ngược.

QJWT: ưu/nhược và cách revoke?+

Ưu: stateless, scale ngang tốt (verify bằng chữ ký, không lưu session). Nhược: khó revoke trước hạn, payload đọc được (chỉ ký không mã hoá). Giải pháp revoke: TTL ngắn + refresh token lưu server, hoặc blacklist.

QHS256 vs RS256?+

HS256: HMAC với secret chung — ký và verify cùng secret (đơn giản, nội bộ). RS256: RSA — private key ký, public key verify → nhiều service verify được mà không giữ khoá ký. Verify LUÔN kiểm tra signing method để chống thuật toán "none".

QVì sao không hash mật khẩu bằng SHA-256 trần?+

SHA-256 quá nhanh → brute-force/rainbow table dễ. Dùng bcrypt/argon2/scrypt: có salt và cost factor (chậm có chủ đích) chống dò mật khẩu.
