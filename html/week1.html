Go Core + Memory

Không chỉ "cái gì" mà là "tại sao Go thiết kế như vậy", "cơ chế ẩn hoạt động ra sao", và "khi nào dùng cái gì". Đây là nền tảng để trả lời mọi câu hỏi Go ở tầng senior.

i Overview & TL;DR

Triết lý của Go: simplicity, explicitness, và composition thay vì inheritance. Mọi cơ chế "ẩn" bên dưới (slice growth, map evacuation, interface dispatch, escape analysis) đều phục vụ hai mục tiêu: predictable performance và code dễ đọc. Khi hiểu động cơ thiết kế, bạn sẽ tự suy ra được hành vi thay vì học thuộc.

TL;DR — 12 điều phải nắm chắc
  • Go truyền tham số luôn theo value (copy) — slice/map/channel chỉ là header nhỏ trỏ tới data chung.
  • Slice = {ptr, len, cap}. append khi len==cap mới cấp array mới. Sub-slice chia sẻ backing array.
  • Map = hash table bucket 8 slot, không thread-safe, iterate ngẫu nhiên có chủ đích.
  • Interface = {type, data}. Nil interface ≠ typed-nil. Method set quyết định value/pointer implement.
  • Struct có alignment/padding — thứ tự field ảnh hưởng kích thước.
  • String immutable, UTF-8; len đếm byte; range đi theo rune.
  • Error là value; wrap bằng %w; check bằng errors.Is/As.
  • Defer chạy LIFO, arg evaluate ngay; sửa được named return.
  • Generics dùng GC-shape stenciling + dictionaries, không phải template C++.
  • Escape analysis quyết định stack/heap tại compile-time.
  • Stack goroutine contiguous, growable (2KB → copy khi đầy).
  • Go memory model: không đồng bộ = không đảm bảo thứ tự thấy được giữa goroutine.

0 Nền tảng: Value Semantics & Type System

Trước khi đi vào từng type, phải hiểu nguyên lý xuyên suốt Go: mọi thứ được truyền theo value. Không có "pass by reference" trong Go — chỉ có pass-by-value, trong đó value đôi khi là một pointer.

Tại sao Go chọn value semantics?
  • Dễ suy luận: khi gọi f(x), bạn biết x không bị thay đổi trừ khi truyền pointer rõ ràng. Không có aliasing ngầm.
  • Tối ưu escape analysis: compiler biết value không escape → cấp phát trên stack → không tạo áp lực GC.
  • Cache-friendly: value nằm liền kề trong bộ nhớ, tận dụng CPU cache tốt hơn con trỏ rải rác (pointer chasing).

"Reference types" thực chất là gì?

Nhiều người gọi slice, map, channel là "reference type". Chính xác hơn: chúng là value type chứa một pointer bên trong. Khi copy, bạn copy cái header nhỏ nhưng vẫn trỏ về cùng data.

1 Variables, Zero Values & Constants

Zero Value — "không có null pointer exception về logic"

Mọi biến trong Go được khởi tạo zero value nếu không gán rõ ràng. Đây là quyết định thiết kế quan trọng.

Tại sao có zero value?

Loại bỏ trạng thái "uninitialized" (nguồn bug lớn trong C/C++). Mọi type có một giá trị hợp lệ mặc định, giúp struct dùng được ngay mà không cần constructor. Đây là nền tảng của idiom "make the zero value useful" (vd: sync.Mutex{}, bytes.Buffer{} dùng được ngay).

TypeZero value
số (int, float)0
boolfalse
string"" (không phải nil)
pointer, slice, map, chan, func, interfacenil
structstruct với mọi field zero
Bẫy: nil map vs nil slice

Đọc từ nil map OK (trả zero value), nhưng ghi vào nil map → panic. Ngược lại, append vào nil slice hoàn toàn OK (Go tự cấp phát).

var m map[string]int   // nil
_ = m["x"]              // OK → 0
m["x"] = 1            // PANIC: assignment to entry in nil map

var s []int            // nil
s = append(s, 1)       // OK → [1]

Constants & iota

Constant trong Go được đánh giá tại compile-time và có thể là untyped — cho phép độ chính xác tùy ý cho tới khi được gán.

const (
    _  = iota             // 0, bỏ qua
    KB = 1 << (10 * iota)  // 1 << 10 = 1024
    MB                       // 1 << 20
    GB                       // 1 << 30
)
Cơ chế untyped constant

const x = 1 << 40 hợp lệ dù vượt int32, vì untyped constant có độ chính xác ít nhất 256 bit. Chỉ khi gán vào biến có type cụ thể mới bị kiểm tra tràn. Điều này cho phép viết math.Pi chính xác cao dùng được cho cả float32 lẫn float64.

2 Pointers

Go có pointer nhưng không có pointer arithmetic (trừ khi dùng unsafe). Đây là lựa chọn thiết kế then chốt.

Tại sao Go có pointer?

  • Cho phép mutate giá trị của caller (in-place).
  • Tránh copy struct lớn.
  • Biểu diễn "optional" (nil = vắng mặt).
  • Chia sẻ state giữa các phần code.

Tại sao KHÔNG có pointer arithmetic?

  • An toàn bộ nhớ — không thể trỏ ra ngoài vùng hợp lệ.
  • Cho phép GC di chuyển stack (contiguous stack) mà không phá pointer.
  • Đơn giản hóa mô hình cho lập trình viên.
Cơ chế ẩn: pointer & GC

Vì không có pointer arithmetic, GC luôn biết chính xác đâu là pointer, đâu là data. Điều này cho phép precise GC (không phải conservative như một số ngôn ngữ khác) và cho phép runtime di chuyển goroutine stack (khi stack grow) rồi cập nhật lại toàn bộ pointer trỏ vào stack đó.

new(T) vs &T{}

CáchTrả vềGhi chú
new(T)*T trỏ tới zero valueHiếm dùng, thường cho type cơ bản
&T{...}*T với field khởi tạoIdiomatic, phổ biến
Best practice

Không "sợ" pointer nhưng cũng đừng lạm dụng. Trả pointer khi: struct lớn, cần mutate, hoặc cần biểu diễn nil. Trả value khi: struct nhỏ immutable. Việc trả pointer thường khiến biến escape lên heap → tăng GC (xem mục 11).

3 Slice — Deep Dive

Slice là type được hỏi nhiều nhất. Phải hiểu tới mức dự đoán chính xác giá trị sau mỗi thao tác.

Bản chất: Slice Header
type slice struct {
    array unsafe.Pointer  // trỏ tới phần tử đầu trong backing array
    len   int             // số phần tử truy cập được
    cap   int             // số phần tử tối đa từ array[0] tới hết backing
}
slice := make([]int, 3, 6)

000 ???
len = 3 (đọc/ghi được) cap = 6 (đã cấp phát)
Tại sao tách len và cap?

len = phần bạn được phép đọc/ghi. cap = phần đã cấp phát sẵn. Tách hai giá trị cho phép append ghi vào vùng đã cấp mà chưa dùng, tránh cấp phát lại liên tục → amortized O(1) append.

Cơ chế append & Growth Algorithm

Kiểm tra capacity
Nếu len < cap: ghi vào array[len], tăng len. Không cấp phát mới → cực nhanh.
Hết capacity → tính cap mới
Runtime gọi growslice. Áp dụng công thức tăng trưởng (xem dưới).
Cấp array mới & copy
Cấp backing array mới, copy toàn bộ phần tử cũ sang, rồi ghi phần tử mới.
Trả slice header mới
Pointer bây giờ trỏ tới array mới. Slice cũ (nếu còn ai giữ) vẫn trỏ array cũ.
Growth algorithm (Go 1.18+)
  • Nếu cap cần thiết > 2× cap hiện tại → dùng luôn cap cần thiết.
  • Nếu cap hiện tại < 256 → gấp đôi.
  • Nếu cap ≥ 256 → tăng theo công thức mượt: newcap += (newcap + 3*256) / 4 (xấp xỉ +25%, hội tụ dần từ 2× về 1.25×).
  • Cuối cùng làm tròn theo size class của memory allocator (nên cap thực tế có thể lớn hơn số bạn nghĩ).

Lưu ý: trước Go 1.18 ngưỡng là 1024 và tăng đúng 25%. Đừng học thuộc con số tuyệt đối — hãy hiểu ý tưởng: nhỏ thì gấp đôi (giảm số lần realloc), lớn thì tăng chậm hơn (tiết kiệm bộ nhớ).

Khi len==cap: cấp backing MỚI, copy 1,2,3 rồi ghi 4. Array cũ còn sống nếu slice khác trỏ vào, không thì bị GC. Đây là gốc rễ của aliasing trap.

Aliasing Trap — câu hỏi kinh điển

a := []int{1, 2, 3, 4, 5}
b := a[1:3]           // b=[2,3]  len=2 cap=4 (từ index 1 tới hết backing)
b = append(b, 99)     // cap còn dư → ghi đè a[3]=99, KHÔNG cấp mới
// a = [1 2 3 99 5]   ← a bị thay đổi!
// b = [2 3 99]

Nguyên nhân

b chia sẻ backing array với a và còn dư cap. append ghi vào ô kế tiếp — chính là a[3].

Cách chặn: 3-index slice

b := a[1:3:3] → cap=2 (=max−low). Append buộc cấp array mới, a an toàn.

Slice Memory Leak

// BAD: giữ 1 byte nhưng ghim cả 10MB không cho GC
func firstByte(huge []byte) []byte {
    return huge[:1]   // backing 10MB vẫn reachable
}
// GOOD: copy → tách khỏi backing lớn
func firstByte(huge []byte) []byte {
    out := make([]byte, 1)
    copy(out, huge[:1])
    return out
}

Ưu điểm slice

  • Linh hoạt, kích thước động.
  • Truyền rẻ (chỉ copy 24 bytes header).
  • Append amortized O(1).
  • Sub-slice zero-copy.

Nhược / cạm bẫy

  • Aliasing ngầm gây bug khó thấy.
  • Có thể ghim backing array lớn (leak).
  • Growth gây realloc + copy nếu không pre-allocate.
  • Không thread-safe khi ghi đồng thời.
Best practices
  • Pre-allocate khi biết size: make([]T, 0, n) → tránh realloc lặp lại.
  • Dùng 3-index slice khi trả sub-slice ra ngoài để tránh aliasing.
  • copy khi cần tách khỏi backing lớn.
  • Xóa phần tử giữ thứ tự: s = append(s[:i], s[i+1:]...); không giữ thứ tự (nhanh hơn): swap với phần tử cuối rồi cắt.

4 Map — Deep Dive

Cấu trúc: hmap + bmap (bucket)
type hmap struct {
    count     int            // len(map)
    B         uint8          // số bucket = 2^B
    hash0     uint32         // seed hash ngẫu nhiên (mỗi map khác nhau)
    buckets   unsafe.Pointer // mảng 2^B bucket
    oldbuckets unsafe.Pointer // buckets cũ khi đang grow
    nevacuate uintptr        // tiến độ di dời
}
type bmap struct {  // mỗi bucket giữ 8 cặp
    tophash [8]uint8    // 8 bit cao của hash mỗi key
    // keys[8], values[8], overflow *bmap  (bố trí ngầm)
}
Tại sao bucket chứa 8 slot & lưu keys/values tách riêng?
  • 8 slot: khớp với 64-bit word của tophash → so sánh nhanh 8 key cùng lúc, tận dụng cache line.
  • keys gộp rồi tới values (không xen kẽ key/value): tránh padding do alignment khi key và value có size khác nhau → tiết kiệm bộ nhớ. Đây là chi tiết tối ưu ẩn ít người biết.

Cơ chế lookup m[key]

Hash key
Tính hash(key, hash0). Dùng B bit thấp để chọn bucket.
So khớp tophash
Lấy 8 bit cao của hash so với mảng tophash[8] trong bucket — reject nhanh slot không khớp mà không cần so sánh full key.
So sánh key đầy đủ
Với slot tophash khớp, so sánh key thật sự (xử lý hash collision).
Overflow bucket
Nếu bucket đầy 8 slot, đi tiếp theo con trỏ overflow (linked list).

Incremental Growth (Evacuation)

Cơ chế ẩn: tại sao grow không giật lag

Khi load factor > 6.5 hoặc quá nhiều overflow bucket, map cần grow gấp đôi số bucket. Nhưng thay vì di dời toàn bộ cùng lúc (gây pause dài), Go dùng incremental evacuation: giữ oldbuckets, và mỗi lần insert/delete di dời 1–2 bucket từ old sang new. Sau khi hết, oldbuckets được giải phóng. Nhờ vậy chi phí grow được trải đều, mỗi thao tác vẫn amortized O(1).

Không thread-safe & iteration ngẫu nhiên

Concurrent access → panic

Runtime có cờ hashWriting; nếu phát hiện ghi đồng thời → fatal error: concurrent map writes. Đây là panic không recover được, không phải data race thường.

Vì sao iterate ngẫu nhiên?

hash0 khác nhau + điểm bắt đầu iterate ngẫu nhiên. Cố ý để lập trình viên không phụ thuộc vào thứ tự — nếu cần thứ tự phải tự sort key.

Giải pháp concurrent: Mutex vs sync.Map

Giải phápKhi nào dùngCơ chế
Mutex + mapMặc định, write nhiềuLock toàn map
RWMutex + mapRead >> writeNhiều reader song song, 1 writer
sync.MapKey ổn định / disjoint keys per goroutineread map (lock-free) + dirty map
sync.Map hoạt động thế nào?

Giữ 2 map bên trong: read (atomic, đọc không cần lock) và dirty (có lock). Read hit → không lock. Read miss nhiều lần → promote dirty thành read. Tối ưu cho đọc nhiều, key ít thay đổi. Ghi mới liên tục thì chậm hơn Mutex+map do overhead duy trì 2 map.

Không lấy được địa chỉ phần tử map

&m["a"] → compile error. Vì evacuation có thể di dời phần tử sang địa chỉ khác → pointer sẽ dangling. Muốn mutate: lấy ra, sửa, gán lại; hoặc dùng map[K]*V.

5 Struct, Memory Layout & Embedding

Alignment & Padding — cơ chế ẩn ảnh hưởng size

CPU đọc bộ nhớ theo word (thường 8 byte). Field phải aligned theo size của nó. Compiler chèn padding để đảm bảo, nên thứ tự field ảnh hưởng kích thước struct.

Bố trí kém — 24 bytes

struct {
  a bool   // 1 + 7 pad
  b int64  // 8
  c bool   // 1 + 7 pad
}

Bố trí tốt — 16 bytes

struct {
  b int64  // 8
  a bool   // 1
  c bool   // 1 + 6 pad
}
a1B
pad7B
b8B
c1B
pad7B
Bố trí kém: field bool xen giữa int64 tạo padding thừa.
Best practice

Sắp field từ lớn tới nhỏ (int64/pointer → int32 → int16 → bool) để giảm padding. Với struct dùng số lượng cực lớn (hàng triệu), việc này tiết kiệm đáng kể RAM. Công cụ: fieldalignment (govet) tự phát hiện.

Embedding — Composition thay vì Inheritance

type Logger struct{ prefix string }
func (l *Logger) Log(msg string) { ... }

type Server struct {
    *Logger          // embedded — không có tên field
    addr string
}
s.Log("hi")  // method promoted — gọi trực tiếp qua Server
Tại sao composition, không inheritance?
  • Tránh "fragile base class" và cây kế thừa sâu khó bảo trì.
  • Method promotion cho khả năng tái dùng mà không tạo quan hệ "is-a" cứng nhắc.
  • Kết hợp tốt với interface: struct tự động thỏa interface nếu embedded type thỏa.
Embedding ≠ subtyping

Server KHÔNG phải là Logger. Nếu hàm nhận *Logger, không truyền thẳng *Server được (phải s.Logger). Promotion chỉ áp dụng cho method/field, không phải quan hệ type.

6 Interface — Deep Dive

Hai biểu diễn: eface & iface
// interface{} / any — không method
type eface struct {
    _type *_type          // mô tả type động
    data  unsafe.Pointer  // trỏ tới value
}
// interface có method
type iface struct {
    tab  *itab            // itab = interface type + concrete type + method table
    data unsafe.Pointer   // trỏ tới value
}
type itab struct {
    inter *interfacetype  // interface nào
    _type *_type          // concrete type nào
    hash  uint32          // để type switch nhanh
    fun   [1]uintptr       // bảng con trỏ hàm (variable length)
}
Dynamic dispatch hoạt động thế nào

Gọi i.Method(): runtime lấy itab.fun[k] (con trỏ tới implementation của concrete type) rồi gọi gián tiếp với data làm receiver. itab được cache theo cặp (interface, concrete type) nên chỉ tính 1 lần.

Nil Interface vs Typed Nil — bug #1 trong Go

func doWork() error {
    var err *MyError = nil
    return err          // trả interface {type:*MyError, data:nil}
}
if doWork() != nil {   // TRUE! vì type field khác nil
    // nhánh này chạy dù "không có lỗi"
}
Tại sao lại vậy?

Interface value = cặp (type, data). Nó chỉ == nil khi cả hai đều nil. Gán một *MyError nil vào error khiến type field = *MyError (non-nil), data = nil → interface KHÔNG nil.

Cách tránh

Luôn return nil trực tiếp khi không lỗi. Đừng khai báo biến concrete pointer rồi return. Nếu buộc phải, kiểm tra và trả nil tường minh.

Nếu T (không addressable, vd giá trị trong map hay return value) được phép có pointer-receiver method trong method set, Go sẽ phải tự động lấy địa chỉ của một value tạm — mutate lên bản copy đó vô nghĩa. Type Assertion & Type Switch

v, ok := i.(string)   // dạng comma-ok: an toàn, không panic
v := i.(string)       // panic nếu sai type

switch x := i.(type) {
case int:    // x là int
case string: // x là string
}
Chi phí

Type assertion so sánh itab.hash / pointer type — rất nhanh (vài ns). Nhưng lạm dụng type switch trong hot path là dấu hiệu thiết kế nên dùng interface method hoặc generics thay thế.

Ưu điểm interface

  • Decoupling — code phụ thuộc hành vi, không phụ thuộc implementation.
  • Dễ test (mock qua interface nhỏ).
  • Duck typing tĩnh: implement ngầm, không cần implements.

Nhược điểm

  • Method call gián tiếp (~2-3ns), không inline được.
  • Đưa value vào interface thường gây heap escape (boxing).
  • Interface lớn khó implement/test.
Best practices (idiomatic)
  • "Accept interfaces, return structs" — hàm nhận interface (linh hoạt), trả concrete type (rõ ràng).
  • Interface nhỏ, tập trung 1 hành vi (io.Reader, io.Writer). "The bigger the interface, the weaker the abstraction."
  • Định nghĩa interface ở nơi dùng (consumer), không phải nơi implement.

8 Error Handling

Triết lý: errors are values

Go không dùng exception cho luồng lỗi thông thường. Lỗi là giá trị trả về bình thường → luồng xử lý tường minh, không có control flow "nhảy" ẩn. Đánh đổi: verbose (if err != nil nhiều), nhưng dễ đọc và không bỏ sót lỗi.

  • Wrap khi thêm ngữ cảnh: fmt.Errorf("query user %d: %w", id, err).
  • Chỉ wrap 1 lần mỗi tầng, tránh chuỗi lỗi quá dài lặp thông tin.
  • Sentinel cho lỗi cần so sánh; typed error khi cần mang dữ liệu (code, field).
  • Không log và return cùng lúc (double logging) — chọn một tầng để log.
  • Panic chỉ cho lỗi lập trình (bug), không cho lỗi vận hành (file not found).

9 Defer / Panic / Recover

Ba quy tắc defer

LIFO

Tham số của hàm defer được tính tại lúc gặp defer, không phải lúc chạy.
Sửa được named return
Closure defer có thể đọc/ghi named return value.
func f() (x int) {   // named return
    defer func(){ x++ }()
    return 5            // gán x=5, defer tăng → trả về 6
}
func g() {
    x := 0
    defer fmt.Println(x)  // in 0 (đã "chụp" x lúc này)
    x = 10
}
Cơ chế ẩn: open-coded defers (Go 1.14+)

Trước đây mỗi defer tạo một record đẩy vào linked list runtime → chậm. Từ Go 1.14, nếu số defer biết trước tại compile-time (không nằm trong loop), compiler dùng open-coded defers: chèn thẳng lời gọi vào cuối hàm + dùng bitmask để biết defer nào cần chạy. Kết quả: defer gần như zero-cost trong trường hợp thường gặp. Defer trong vòng lặp thì vẫn dùng cơ chế heap cũ (chậm hơn).

Bẫy: defer trong loop

for { defer f.Close() } → các Close dồn tới cuối hàm, không đóng ngay → rò rỉ file descriptor. Giải pháp: bọc thân loop trong 1 hàm/closure, hoặc gọi Close tường minh.

Panic / Recover

Luồng panic

Panic dừng thực thi bình thường, chạy các defer đã đăng ký (unwind stack). Nếu một defer gọi recover(), panic dừng lại và hàm trả về bình thường từ điểm đó. Nếu không có recover, panic lan tới top của goroutine → crash toàn chương trình.

func safeHandler() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("recovered: %v", r)
        }
    }()
    mightPanic()
}
Best practices
  • Dùng panic cho bug không thể tiếp tục (invariant bị phá), không cho lỗi thường.
  • Recover ở ranh giới: HTTP middleware, worker goroutine — tránh 1 request làm sập server.
  • recover() chỉ hiệu lực khi gọi trực tiếp trong defer.
  • Panic ở goroutine khác KHÔNG bị recover ở goroutine cha bắt được.

11 Stack / Heap / Escape Analysis

Stack — nhanh, tự dọn, không GC Heap — chậm hơn, GC quản lý, chia sẻ được

Contiguous, Growable Stack

Cơ chế: stack goroutine grow thế nào

Mỗi goroutine khởi đầu stack chỉ ~2KB. Khi gần đầy, runtime cấp một stack mới lớn gấp đôi, copy toàn bộ nội dung sang, và cập nhật mọi pointer trỏ vào stack cũ (làm được nhờ không có pointer arithmetic + precise GC). Stack cũng có thể co lại khi dùng ít. Nhờ vậy Go chạy được hàng triệu goroutine mà không tốn RAM như thread OS (mỗi thread ~1-8MB stack cố định).

Stack

  • Cấp phát = dịch con trỏ (1 lệnh).
  • Giải phóng tự động khi hàm return.
  • Không tạo việc cho GC.
  • Cache-friendly (liền kề).

Heap

  • Cần allocator (tcmalloc-style).
  • GC phải trace & thu hồi.
  • Sống lâu, chia sẻ giữa goroutine.
  • Pointer chasing → cache miss.

Mục đích

Value vs Pointer — quyết định cuối cùng

Ưu tiên VALUE khi

  • Struct nhỏ (≤ ~64 bytes).
  • Không cần mutate.
  • Muốn stack allocation / tránh GC.
  • Immutable, an toàn concurrent read.

Ưu tiên POINTER khi

  • Struct lớn (copy đắt).
  • Cần mutate in-place.
  • Chia sẻ state / biểu diễn nil.
  • Implement interface với pointer receiver.
Nguyên tắc & Go memory model (bonus)
  • Đo trước khi tối ưu: đừng đoán stack/heap — dùng -gcflags="-m" và pprof (Week 3).
  • Consistency > micro-optimization: chọn value hoặc pointer receiver nhất quán cho một type.
  • Go memory model: nếu không có đồng bộ (channel, mutex, atomic), không đảm bảo goroutine này thấy được ghi của goroutine kia. "Đừng giao tiếp bằng chia sẻ bộ nhớ; hãy chia sẻ bộ nhớ bằng cách giao tiếp." (chi tiết ở Week 2).

? Flashcards — Tự kiểm tra

Che đáp án, tự trả lời thành tiếng như đang phỏng vấn, rồi click để đối chiếu.

QGo pass-by-value hay pass-by-reference? Vậy slice thì sao?+

Luôn pass-by-value. Slice là value type chứa header {ptr,len,cap}; copy header nhưng backing array dùng chung. Nên sửa phần tử ảnh hưởng caller, nhưng append có thể không (nếu realloc).

QDự đoán: a:=[]int{1,2,3,4,5}; b:=a[1:3]; b=append(b,99)+

a=[1,2,3,99,5], b=[2,3,99]. Vì cap(b)=4>len(b)=2, append ghi đè a[3]. Chặn bằng a[1:3:3].

QGrowth algorithm của slice? Con số tuyệt đối có quan trọng?+

Ý tưởng: cap nhỏ (<256) gấp đôi để giảm số lần realloc; cap lớn tăng ~25% để tiết kiệm RAM; rồi làm tròn theo size class allocator. Con số cụ thể thay đổi giữa các version — hiểu ý tưởng quan trọng hơn học thuộc.

QVì sao map không cho lấy &m["a"]?+

Incremental evacuation khi grow có thể di dời phần tử sang địa chỉ khác → pointer sẽ dangling. Nên Go cấm lấy địa chỉ. Muốn mutate: dùng map[K]*V hoặc get-modify-set.

QTại sao map iterate ngẫu nhiên? Có phải bug?+

Cố ý. Hash seed hash0 ngẫu nhiên + điểm bắt đầu ngẫu nhiên. Mục đích: buộc lập trình viên không phụ thuộc thứ tự. Cần thứ tự → tự sort keys.

Qsync.Map hoạt động thế nào và khi nào dùng?+

Giữ 2 map: read (atomic, lock-free) + dirty (có lock). Read hit không cần lock. Tối ưu cho đọc nhiều / key ổn định / disjoint keys. Ghi mới liên tục thì chậm hơn Mutex+map.

QNil interface vs typed nil?+

Interface là cặp (type,data), chỉ ==nil khi cả hai nil. Trả một *MyError nil qua error → type field non-nil → interface KHÁC nil. Fix: return nil trực tiếp.

QVì sao pointer-receiver method không nằm trong method set của T?+

Vì gọi trên value không addressable (map element, return value) sẽ mutate lên bản copy tạm — vô nghĩa. Go cấm để tránh bug ngầm. Nên var a Animal = Dog{} lỗi nếu method là pointer receiver.

QThứ tự field struct ảnh hưởng gì?+

Alignment/padding: field phải aligned theo size → compiler chèn padding. Sắp từ lớn tới nhỏ giảm padding → struct nhỏ hơn. Với hàng triệu instance, tiết kiệm RAM đáng kể.

Qlen(s) của "世界" là bao nhiêu?+

6 (mỗi ký tự CJK = 3 bytes UTF-8). len đếm byte. len([]rune("世界")) = 2. range đi theo rune.

Q%w vs %v khi format error?+

%w wrap giữ chain → errors.Is/As hoạt động. %v chỉ ra string, phá chain → không unwrap được.

QOutput: func f()(x int){ defer func(){x++}(); return 5 }+

Trả về 6. Named return: return 5 gán x=5, rồi defer tăng x lên 6 trước khi hàm thực sự trả về.

QOpen-coded defers là gì?+

Từ Go 1.14: nếu số defer biết trước compile-time (không trong loop), compiler chèn thẳng lời gọi + bitmask → defer gần như zero-cost. Defer trong loop vẫn dùng cơ chế heap chậm hơn.

QGo generics được compile thế nào? Giống C++ template?+

Không. Dùng GC-shape stenciling + dictionaries: type cùng memory shape share 1 bản code, type info truyền qua dictionary runtime. Cân bằng giữa code bloat (C++) và boxing chậm (Java). Có overhead nhẹ do gián tiếp.

QKể 5 trường hợp biến escape lên heap.+

1) return &localVar. 2) gán vào interface (boxing). 3) gửi pointer qua channel. 4) closure capture. 5) make với size runtime / biến quá lớn. Kiểm tra: go build -gcflags="-m".

QGoroutine stack khởi đầu bao nhiêu và grow ra sao?+

~2KB. Khi gần đầy: cấp stack mới ×2, copy toàn bộ, cập nhật mọi pointer (nhờ precise GC + không có pointer arithmetic). Có thể co lại. Cho phép hàng triệu goroutine.
